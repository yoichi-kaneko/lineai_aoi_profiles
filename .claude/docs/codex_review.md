# codex レビュー：依頼文の組み立てと反映の作法

碧衣が生成した成果物（画像生成プロンプト・SNS 投稿本文）を、外部のレビュアーである **Codex CLI** へ渡し、**一往復だけ**見てもらうための手順書です。実行そのものは [`review_with_codex`](../skills/review_with_codex/SKILL.md) スキルが担い、本ファイルは**依頼文に何を書くか**と**返ってきた指摘をどう扱うか**を定めます。

呼び出し元は次の3箇所です。

| 観点セット | 対象 | 呼び出し元 |
|---|---|---|
| `image_prompt` | 小夜・帰灯の画像生成プロンプト | [画像生成ガイドライン](../../assets/image_guideline.md) セクション3の共通手順3 |
| `scribe_image_prompt` | 綴葉のレポート画像プロンプト | [綴葉モード](../../modes/scribe.md) ステップ4の手順3 |
| `scribe_post` | 綴葉の SNS 投稿本文 | [綴葉モード](../../modes/scribe.md) ステップ5の手順4 |

---

## 1. 依頼文を書くときの大前提

### 碧衣の語彙で書かない

レビュアーは碧衣の世界観を知らない外部の道具です。依頼文は**素直な技術文書**として書いてください。[aoi_messaging.md](../rules/aoi_messaging.md) の「ルミナス・ログ」の語彙リライトは、ユーザーへ届く言葉に対する作法であり、**この依頼文は対象外**です。ホログラム・ルリ・蛍・オペレーションウェアといった語を説明なしに持ち込むと、レビュアーが文脈を取り違えて的外れな指摘を返します。

### 依頼文だけで判断できるようにする（自己完結）

レビュアーにリポジトリを読ませません。判断に要る前提は、すべて依頼文の中へ書き込んでください。依頼文の冒頭に、次の趣旨の一文を必ず置きます。

> ファイルの読み取りやコマンドの実行は行わず、この依頼文に書かれた情報だけで判断してください。

これは所要時間を安定させるためでもあり、レビュアーが不要な情報に触れないようにするためでもあります。

### パスを書かない

プロジェクトのディレクトリパスや、リポジトリ内のファイルパスを依頼文に書かないでください。プロンプト本文に現れる参考画像のファイル名（`base.png` など）はそのままで構いませんが、それらがどこにあるかは書きません。

## 2. 依頼文の共通の骨格

`tmp/codex_review_input.md` に、次の7ブロックをこの順で書き出します。

| # | 見出し | 中身 |
|---|---|---|
| 1 | `# レビュー依頼` | レビュアーの役割の宣言と、上記「ファイルを読まない」の一文 |
| 2 | `## 成果物の送り先` | この成果物がどこへ送られるか（下の観点セットごとの定型文） |
| 3 | `## 前提条件` | 変更できない所与の条件（下の観点セットごとの定型文＋その回の可変情報） |
| 4 | `## レビュー観点` | 下の観点セットの箇条書きをそのまま置く |
| 5 | `## 指摘してほしくないこと` | 下の共通リストをそのまま置く |
| 6 | `## 出力形式` | 下の定型文をそのまま置く |
| 7 | `## 対象` | 成果物の全文をコードフェンスで囲んで置く |

### ブロック6「出力形式」の定型文

```markdown
## 出力形式

- 指摘は重要な順に、**最大5件**まで。些細な言い回しの好みは挙げないでください。
- 各指摘は次の3点を1行ずつで書いてください。

  - **箇所**: 対象のどの部分か（引用は20字程度まで）
  - **問題**: 何が読み手（送り先）にとって不都合か
  - **修正案**: 置き換える具体的な文言

- 修正すべき点が無ければ、「指摘なし」の1行だけを返してください。
- 前置き・要約・総評は不要です。指摘だけを返してください。
```

### ブロック5「指摘してほしくないこと」の共通リスト

観点セットによらず、次をそのまま置きます（`scribe_post` のときは最後の1項目も加えます）。

```markdown
## 指摘してほしくないこと

以下は決定済みの前提であり、レビューの対象外です。これらへの指摘は返さないでください。

- 登場人物の設定・世界観・固有名詞の是非
- 主題・衣装・登場人物の選択そのもの（別途の抽選で決定済みです）
- 文体・敬体・語尾の好み（文末に「！」を使わない等の制約は所与です）
- 記述されている事実そのものの真偽（あなたは元の資料を持っていません）
```

`scribe_post` の場合は、上のリストに次を加えます。

```markdown
- ハッシュタグの追加・変更（`#YAMAP #碧衣の代筆` の2つに固定です）
```

## 3. 観点セット `image_prompt`（小夜・帰灯）

### ブロック2「成果物の送り先」

```markdown
## 成果物の送り先

以下のテキストは、OpenAI の画像生成モデル **GPT Image 2（`gpt-image-2`）** へ、画像生成リクエストのプロンプトとしてそのまま送られます。人間が読む文章ではなく、画像生成モデルへの指示文としてレビューしてください。
```

### ブロック3「前提条件」

定型部分に加え、**その回の可変情報**（添付する参考画像のファイル名と役割）を書きます。

```markdown
## 前提条件

以下は変更できない条件です。これらを前提にレビューしてください。

- 出力画像のサイズは **1536x1024（横長）固定**です。
- プロンプトは日本語で記述します。
- プロンプトと同時に、キャラクター・衣装・舞台の設定資料画像を添付します。今回添付するのは次のとおりです。
  - （例）`base.png` — 主役キャラクターの容姿の正。同一性を保つための資料
  - （例）`outfit_d.png` — 今回の衣装（ルームウェア）の設定資料
  - （例）`room_night.png` — 舞台となる部屋の夜の情景の設定資料
- プロンプトは次の5ブロックの順で構成する決まりです。この順序自体は変更できません。
  ① 対象キャラクター ② 衣装と装備 ③ 構図とカメラワーク ④ 時間帯と天気の演出 ⑤ スタイルと品質
```

添付画像の行は、その回に実際に渡すファイルリストへ置き換えてください。役割の説明は1行で足ります。

### ブロック4「レビュー観点」

```markdown
## レビュー観点

1. **アングル・カメラワーク**: ショットサイズ（寄り・引き）とカメラ方向の指定が互いに矛盾せず、画像生成モデルが一意に解釈できる具体度で書かれているか。
2. **オブジェクトの位置関係**: 主役・小物・背景要素の前後関係、左右の配置、画面内のどこに置くかが、破綻なく特定できるように書かれているか。画面内にあるのか画面外なのかが曖昧な要素はないか。
3. **説明の順序と構成**: 上記5ブロックの中で、後段の記述が前段の指定を打ち消していないか。同じ指定の重複、冗長な言い換え、相互に矛盾する記述はないか。
4. **参考画像への参照**: 添付画像の役割（同一性の維持なのか、意匠の参照だけなのか）が、プロンプト本文の記述と明確に結び付いているか。
5. **曖昧・多義的な表現**: 画像生成モデルが取り違えうる表現、複数の解釈が成り立つ表現はないか。
```

## 4. 観点セット `scribe_image_prompt`（綴葉のレポート画像）

### ブロック2「成果物の送り先」

`image_prompt` と同じ定型文を使います。

### ブロック3「前提条件」

```markdown
## 前提条件

以下は変更できない条件です。これらを前提にレビューしてください。

- 出力画像のサイズは **1536x1024（横長）固定**です。
- プロンプトは日本語で記述します。
- これは登山レポートを1枚にまとめた**レポート風レイアウト画像**であり、レイアウトの雛形となるテンプレート画像を添付して、その配置・配色・作画スタイルを踏襲させます。
- 添付するのは次の4点です。
  - `report_template.png` — レイアウト・配色・作画スタイルの正
  - `report_designs_1.png` — 装飾チップ集(1)：キャラクター・道具類
  - `report_designs_2.png` — 装飾チップ集(2)：地形・天候アイコン・季節装飾
  - 代表写真1枚 — レイアウトの写真エリアへそのまま配置する実写。内容の改変は不可
- 画像内に描く文字はすべて日本語で、**一字一句そのまま描画させる**方式です。文言そのものの良し悪しではなく、指示として一意に伝わるかを見てください。
- 生成後、画像の右下隅へ QR コードを別工程で重ねます。そのためプロンプトには「右下・左下の隅を余白として空ける」指示が入ります。QR コード自体を描かせてはいけません。
- プロンプトは次の5ブロックの順で構成する決まりです。この順序自体は変更できません。
  ① レイアウトの踏襲 ② 差し込みテキスト ③ 代表写真の配置 ④ チップの散りばめ ⑤ スタイル・品質と末尾の注意文
```

### ブロック4「レビュー観点」

```markdown
## レビュー観点

1. **レイアウト踏襲の具体度**: テンプレート画像のどの領域に何を置くのかが、対応を取れる具体度で書かれているか。
2. **差し込みテキストの一意性**: どの文字列をどの領域へ描くのかが一意に定まるか。領域の指定漏れ、どの領域か読み取れない文字列はないか。
3. **代表写真の扱い**: 写真の内容を改変させない旨が明確に伝わるか。描き足し・置き換え・イラスト化を招きうる表現が混じっていないか。
4. **チップと天候アイコンの指示の競合**: 装飾を散りばめる指示と、天候アイコンを特定のものへ置き換える必須指示が、互いに競合していないか。
5. **隅の余白確保との矛盾**: 右下・左下の隅を空ける指示と、他の配置指示（キャラクターや文字の位置）が矛盾していないか。
6. **説明の順序と構成**: 上記5ブロックの中で、後段の記述が前段の指定を打ち消していないか。重複・冗長・相互矛盾はないか。
```

## 5. 観点セット `scribe_post`（綴葉の SNS 投稿本文）

### ブロック2「成果物の送り先」

```markdown
## 成果物の送り先

以下のテキストは、**X（旧 Twitter）へ公開投稿する本文**です。フォロワーを含む不特定多数が読みます。本人に代わって書かれた登山レポートの紹介文であり、読み手はこの投稿以外の文脈を持っていません。
```

### ブロック3「前提条件」

```markdown
## 前提条件

以下は変更できない条件です。これらを前提にレビューしてください。

- 投稿は「本文 → 空行 → ハッシュタグ行 → URL 行」の順で構成します。この構成と順序は変更できません。
- ハッシュタグは2つに固定です。追加・変更はできません。
- 本文（ハッシュタグと URL を除く）は **600字程度が目安**です。元のレポートが短ければ、これより大幅に短くて構いません。
- 本文の冒頭は「登山日」と「登った主要な山」の紹介から切り出す決まりです。登山日と投稿日にはずれがあるため、読み手がいつの山行かを最初に把握できるようにしています。
- 続けて、天候・道の険しさ・眺望を優先して要約します。
- 文体は丁寧な敬体で、文末に「！」は使いません。
- 書き手自身（一人称）を立てず、主語を置かない書き方をします。
```

### ブロック4「レビュー観点」

```markdown
## レビュー観点

1. **全体の構成**: 冒頭（登山日と主要な山）→ 要約（天候・険しさ・眺望）→ ハッシュタグ → URL の流れが崩れていないか。要約の中で優先すべき3点が押さえられているか。
2. **情報の順序**: 前提知識のない読み手が、いつ・どこを・どう歩いてどうだったか、を無理なく順に受け取れるか。後から補足すべき情報が先に出て読みにくくなっていないか。
3. **冗長さ**: 同じ内容の重複、意味の薄い言い換え、削っても伝達が損なわれない箇所はないか。
4. **根拠のない断定**: 本文の中に、示されている事実から飛躍した断定や推測が混じっていないか（事実そのものの真偽ではなく、書きぶりが断定的すぎないかを見てください）。
5. **公開発信としての適切さ**: 個人や家族が特定されうる情報、内輪にしか通じない表現が混じっていないか。
```

## 6. 返ってきた指摘の扱い

### 採否は碧衣が判断する

レビュアーは背景の全体を知りません。次に当たる指摘は**不採用で構いません**。理由をユーザーへ説明する必要もありません。

- ガイドライン（[画像生成ガイドライン](../../assets/image_guideline.md) / [SNS投稿画像ガイドライン](../../assets/scribe_image_guideline.md) / [aoi_messaging.md](../rules/aoi_messaging.md) の SNS 宛の節）と矛盾する指摘
- 「指摘してほしくないこと」に挙げた領域へ踏み込んだ指摘
- 抽選で決まった構図軸・主題・登場人物を覆す指摘
- 事実関係の変更を伴う指摘（レビュアーは元の資料を持っていません）

### 一往復で終える

反映した成果物を**再びレビューへ回さないでください**。指摘を反映したら、そのまま次の手順（画像の生成・SNS への投稿）へ進みます。

### 反映後に確かめること

- **画像プロンプト**: 反映後のプロンプトが、元の構成ブロックの順序を保っていること。`generate_gpt_image` へ渡す添付画像ファイルリストは、レビューでは変更しません。
- **綴葉の画像プロンプト**: 反映内容を `tmp/gpt_image_prompt.txt` へ書き直したうえで生成へ進むこと。
- **SNS 本文**: 「本文 → ハッシュタグ → URL」の順と、ハッシュタグ行・URL 行そのものが失われていないこと。

### レビューが行われなかった場合

`review_with_codex` が `ok` 以外の結果（`skipped` / `unavailable` / `timeout` / `error`）を返した場合は、**レビュー前の成果物のまま次の手順へ進みます**。再試行はしません。詳しくは [`review_with_codex`](../skills/review_with_codex/SKILL.md) の「失敗時の扱い」を参照してください。

### ログへの記録

小夜・帰灯では、レビューの結果を [画像生成ログ（image_logs）](image_log_schema.md) の `codex_review` に記録します。値の対応は次のとおりです。

| 状況 | `codex_review` |
|---|---|
| 指摘を受け、1件以上をプロンプトへ反映した | `applied` |
| 指摘はあったが、すべて不採用と判断した | `not_applied` |
| レビュアーが「指摘なし」と返した | `no_findings` |
| レビューが行われなかった（`ok` 以外） | `skipped` |

綴葉モードは `image_logs` を記録しないため、この記録は不要です。
