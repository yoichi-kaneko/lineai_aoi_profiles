# 山行連絡モードの共通手順（継灯・帰灯）

継灯（`stay_mountain`）・帰灯（`off_mountain`）が共通で用いる判断手順です。取得範囲・報告構成・中断時の扱いは各 `modes/*.md` を正とし、**本ドキュメントは「継灯と帰灯の判別」「山行コンテキストの確定」「時刻の採用優先順位」の正本**とします。

## 1. 継灯と帰灯の判別

どちらのモードに当たるかは、**その日の行動を終えた地点が山中かどうか**で判別します。「翌日に登山予定があるか」は判別の基準になりません。

- **継灯**: その日の行動を終えた地点が、まだ**山中**（山小屋・テント場・避難小屋など）である場合。下山はしておらず、同じ山行が翌日以降も続きます。
- **帰灯**: その日の山行が**下山をもって完結**した場合。下山後に里の宿（ビジネスホテル・旅館など、山中でない宿泊地）へ外泊する場合は、翌日に別の登山予定があっても帰灯として扱います。

連日で別の山を歩く日程では、それぞれが独立した山行です。里の宿を挟んで日帰り登山が続く場合は、日ごとに**門灯 → 帰灯**の組で連絡し、継灯は挟みません。

## 2. 山行コンテキストの確定

山名・コース・入山日・下山予定日を、次の優先順位で確定してください。

**（A）門灯モードの `up_mountain` 記録がある場合 — 計画書 fetch を省略**

Firestore に `type` = `up_mountain` の記録があり、今回の連絡がその山行に対応すると解釈できる場合は、その記録の山名・コース・下山予定日を「登山日程」として採用し、**`fetch_yamap_plan` は実行しない**でください。カレンダー上の予定と食い違う場合のみ、照合のために計画書 fetch を行います。

`up_mountain` の記録日は**本日でなくて構いません**。一泊以上の山行では門灯モードが入山日に実行されるため、**前日以前の `up_mountain` に本日の継灯・帰灯が対応する**のが通常の形です（日帰りなら入山日・下山日ともに本日、一泊以上なら入山予定日〜下山予定日が日程になります）。

**（B）上記に該当しない場合 — 計画書 fetch**

カレンダーの予定から `https://yamap.com/plans/code/${CODE}/printing` 形式のURLを含む登山予定を探してください。1件だけの場合は、**`fetch_yamap_plan` スキル（計画書URL用）**で詳細（山名、入山日、下山日、コース）を取得します。複数ある場合は、計画書を取得する前に、カレンダー上の**同一日**の予定どうしで各URLの `${CODE}` を比較します。コード一致による1本まとめは同一日の予定間だけに限定し、別日に同じ計画URLが載っていても独立した山行候補として扱います。

- **同一日の予定で計画コードがすべて一致する場合**: 同じ内容の予定がユーザーのメンテナンス漏れによって重複登録されたものとみなし、1本の山行にまとめます。`fetch_yamap_plan` は同じ計画URLに対して1回だけ実行し、この重複だけを理由に対象不明とは判断しません。
- **それ以外（同一日で計画コードが異なる、または別日にまたがる）**: それぞれ個別の山行候補として扱います。各URLを `fetch_yamap_plan` に渡し（同じ計画URLへの重複呼び出しは避けてよい）、取得した計画書から、最も早い入山予定日〜最も遅い下山予定日を「取得日程」とします。後続の情報処理でどの山への連絡かを判断してください。

**登山予定が見つからなかった場合の扱いはモードごとに異なります**（ユーザーへ確認を送るか、何も送らず終了するか）。各モードの手順に従ってください。

## 3. 時刻の採用優先順位

家族へ伝える時刻（継灯＝宿泊地への到着時刻、帰灯＝下山時刻）は、以下の優先順位で決定し、**「〇時〇分頃」** のように丸めた表現で本文に含めてください。

1. **ユーザーが明示した時刻を最優先**: 本モードをトリガーした `line_text` に時刻の明示（例:「下山は11:30頃に終わっていました」「山小屋には14:00頃に着きました」）がある場合は、**Swarm や後続のフォールバックより優先して**採用する。山中は電波が届かず、行動の区切りから連絡までに時間差が生じるため、本人の申告が最も実態に近い。連絡が遅れた事情（電波不通など）が読み取れる場合や、当該時刻と連絡時刻に明らかな開きがある場合は、家族が時刻のずれを不審に思わないよう一言添える（例:「電波の届かない道が続いたため、私のもとに便りが届いたのは先ほどでした」）。
2. **Swarm のチェックイン時刻**: 明示がない場合、該当するチェックインがあればその時刻を採用する（帰灯モードでは `modes/off_mountain.md` の「下山地点の判定」を満たすチェックインに限る）。本文では採用根拠となった地点を明示する（例:「登山口に戻った時刻」「○○駅に到着した時刻」）。単に「下山した時刻」とだけ書かず、どの地点・局面の時刻かを家族が誤解なく読めるようにする。
3. **トリガーとなった `line_text` の登録時刻をフォールバックとして使用**: いずれも該当しない場合は、本モードをトリガーした `line_text` の Firestore 登録時刻を採用する。これは実際に便りが碧衣のもとへ届いた時刻であり、報告を作成し始めた時刻とは区別する。取得範囲は各 `modes/*.md` の収集手順を正とし、下山が予定日を過ぎた場合でもトリガー記録が範囲外にならないよう上限を実行日まで広げる。
4. **現在時刻を最後のフォールバックとして使用**: トリガーとなった `line_text` の登録時刻も取得できない場合に限り、報告作成ステップの冒頭で取得した現在時刻を採用する。

帰灯モードで YAMAP の活動記録カードが届いており、カードの「タイム」と門灯モードが記録した行動開始時刻から終了時刻を逆算できる場合は、上記の優先順位で採用した時刻が実態から大きく外れていないかの確認に用いて構いません。逆算値は照合材料であり、上記の採用順位へ新たに加える時刻ではありません。
