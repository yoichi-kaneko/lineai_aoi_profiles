## 注意事項（常時適用ルール）
- メッセージが長くなりすぎないよう、情報は「代表的なもの」に絞ってください。
- 文末に「！」を使用しないでください。

## ツール呼び出しのエラー処理
- ツールの呼び出しが失敗またはエラーを返した場合、**1回だけ**再試行してください。それでも失敗した場合はそのステップをスキップし、次のステップに進んでください。
- 一部の情報が取得できなくても処理を止めず、取得できた情報で最善のメッセージを生成して送信してください。
- 複数のツール呼び出しが連続して失敗した場合は、その旨を「要望のフィードバック」としてTodoistに登録してください。

### タイムアウトの扱い（上の「1回だけ再試行」の例外）

コマンドがタイムアウトした場合（Bashツールの時間切れでバックグラウンドへ回された、終了コード `124`、標準エラーに `[TIMEOUT]` の表示があった、など）は、**「失敗」ではなく「結果が分からない」状態**です。上の再試行ルールをそのまま適用すると、Firestoreの二重書き込みやLINEの二重送信を招くため、以下に従ってください。

**1. まず結果を確かめる**

バックグラウンドへ回されたコマンドは、**そのターンを終える前に完了を確認**してください。ヘッドレス実行では、待たずにターンを終えるとプロセス終了とともに処理ごと失われます（[長時間処理の実行方法](../docs/long_sleep_execution.md) 参照）。

**2. 操作の種別で分岐する**

| 種別 | 該当スキル | タイムアウト時の扱い |
|---|---|---|
| **読み取り** | `get_*` / `download_*` / `fetch_*` | そのまま**1回だけ再試行**してよい（副作用がないため）。それでも駄目ならそのステップをスキップ |
| **書き込み（Firestore）** | `put_firestore_doc` | **すぐに再実行しない**。書き込み時と**同じ `--collection`** で `get_firestore_docs` を呼び、対象の `date` / `type` / `description` を照合して**記録が無いことを確認できた場合に限り**1回だけやり直す。照合できない場合は再実行しない |
| **書き込み（Todoist）** | `put_todoist_task` | **すぐに再実行しない**。`get_todoist_tasks` など Todoist 側の取得で同一タスクの有無を確認し、**無いことを確認できた場合に限り**1回だけやり直す。照合できない場合は再実行しない |
| **送信** | `send_line_text` / `send_line_image` / `send_line_audio` / `post_twitter` | **再送しない**。届いたかどうかを確認する手段がなく、二重送信は未達より影響が大きいため |

**3. 送信がタイムアウトした場合の後始末**

- `line_undelivered` への退避は**行わないでください**。退避すると後続モードが「届かなかった内容」として扱いますが、実際には届いている可能性があります。退避は[送信失敗時の手順](../docs/line_send_fallback.md)のとおり、**明確な失敗（非ゼロ終了・429・クオータ超過など）のときだけ**です。
- 送信結果が不明のまま処理を終える場合は、その旨を「要望のフィードバック」としてTodoistに登録してください（対象のモード・日付・どのスキルがタイムアウトしたかを添える）。

## 一時ファイル（tmp/）の扱い
- `tmp/` 配下は、その処理（モード）の中だけで使う揮発的な作業領域です。前後のモードへ tmp/ 経由で情報を引き継ぐことはありません（引き継ぎは Firestore で行います）。
- 処理の開始時に前回の残存ファイルが存在しても、**内容を確認・参照しないでください**。スキルが指定する固定名の一時ファイル（`tmp/line_message.txt` など）は、毎回 Write で上書きして使えば足ります。
- 残存ファイルの後始末を気にする必要はありません。本番フローでは起動スクリプト側が処理開始時に掃除します。

### 例外：調べ（song）モードのフェーズA→フェーズB引き継ぎ
- 調べモードは headless での長時間待機を避けるため、フェーズA（生成開始）とフェーズB（送信）の2つの `claude -p` 起動に分割され、その間の待機・楽曲ダウンロードを `send_daily_line.sh`（シェル）が担います。
- この**2フェーズ間に限り**、`tmp/` を意図的な引き継ぎ領域として使います。シェルが**フェーズ間では tmp/ を掃除しない**ことで、フェーズAが書き出した `tmp/song_task_id.txt` / `tmp/song_message.txt` / `tmp/song_log.ok`、およびシェルが用意する `tmp/song_audio_path.txt` を、フェーズBが**参照してよい**（上記「内容を確認・参照しない」原則の唯一の例外）。
- これは「同一の調べ処理」を2起動に分けた内部受け渡しであり、別モードへの引き継ぎではありません。手順は [modes/song.md](../../modes/song.md) と `send_daily_line.sh` の song ブロックを正とします。

### 例外：綴葉（scribe）モードの活動記録取得
- 綴葉モードの `fetch_yamap_activity` は代筆の核となる必須素材です。上の「1回だけ再試行 → スキップして次へ」は適用せず、**1回再試行しても取得できない場合（コマンド失敗・本文欠落を含む）は処理を中断**し、ユーザーへ報告して終了してください。
- 手順の正本は [modes/scribe.md](../../modes/scribe.md) のステップ3、および [run_aoi_scribe/SKILL.md](../skills/run_aoi_scribe/SKILL.md) です。
