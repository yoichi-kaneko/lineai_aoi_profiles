# dev_apply_todoist_request

碧衣が「[要望のフィードバック](../../../aoi.md)」として登録した Todoist タスクを読み取り、**要望（タスク本文）と対応方針（コメント）に沿って修正し、PR 提出まで**行う開発用スキルです。

要望はタスクの `content` / `description` に、その要望をどう扱うかというユーザーの判断は `【対応方針】` で始まるコメントに書かれています。**両方が揃って初めて実装に入れます**。

## 概要

- **対象**: 碧衣が登録した要望タスク（開発者が自分で登録した開発タスクでも、同じ運用であれば構わない）
- **入力**: Todoist のタスク URL（複数可）
- **判断基準の正本**: [coding_agent.md](../../coding_agent.md) の「注意事項」
- **Git 操作の委譲先**: [dev_ship_change](../dev_ship_change/SKILL.md)（ブランチ作成・コミット・プッシュ・PR 作成）

## Todoist コメントの運用規約（正本）

Todoist のコメントは、宛先の異なる2種類が同じタスクに並びます。

| 種別 | 宛先 | 目印 | 書く内容 |
|---|---|---|---|
| 対応方針 | 開発フロー（このスキル） | **`【対応方針】` で始める**（`[対応方針]` も可） | その要望を採るか、どう直すか、どこまでやるか |
| 完了報告など | 碧衣 | 目印を付けない | 対応した旨・労い・碧衣に伝えたいこと |

- **1つのコメントに両方を混ぜない。** 対応方針と碧衣宛のメッセージは別コメントに分けて投稿してください
- [get_todoist_comments](../get_todoist_comments/SKILL.md) は**既定で対応方針コメントを除外**します。碧衣の各モードは目印付きのコメントを読みません（除外件数のみ `excludedPolicyComments` として見えます）
- 目印を付け忘れた対応方針は碧衣に読まれますが、[技術・運用連絡の語り方](../../rules/aoi_messaging.md)でぼかされるため実害は限定的です。ただし**このスキルからは方針として認識できない**ため、手順2で「方針が無い」と判定されます

## 前提

- GitHub を操作する手段があること。`gh` が使えるならそれを使い、使えない環境（ブラウザのクラウドセッションなど）では GitHub MCP ツールで代替する（[dev_git_workflow.md](../../docs/dev_git_workflow.md) の「GitHub 操作の手段」）
- `TODOIST_API_TOKEN` が設定されていること。ローカルでは `.env`、ブラウザのクラウドセッションでは環境側の環境変数に置く
- 作業ツリーに、今回の変更と無関係な未コミットの差分が無いこと

## Claudeへの指示

### 1. 対象タスクを確定する

ARGUMENTS を**空白区切りのタスク URL 列**として解釈します。

```text
{スキル名} https://app.todoist.com/app/task/todoist-6hMrP2PjpPv46vQq https://app.todoist.com/app/task/6hCfG9G7P29JHMjH
```

- URL が1件も渡されていない場合は、推測で対象を探さず、ユーザーに確認してください
- URL から ID を取り出す処理は**スクリプト側が行う**ため、渡された URL をそのまま各スキルの引数に使います

### 2. 要望と方針を読み取る

**この手順は全タスク分をまとめて先に行います。** 1件目の実装に入る前に、全件の材料を揃えてください。

各 URL について、次の2つを実行します（タスク間は並列で構いません）。

```bash
pnpm exec tsx src/todoist/get_task.ts "{タスクURL}"
pnpm exec tsx src/todoist/get_comments.ts "{タスクURL}" --include-policy
```

- **`--include-policy` を必ず付けます。** 付けないと対応方針コメントが除外され、方針が読めません
- 取得したタスクの `checked` が `true`（既に完了済み）の場合は、対応済みのタスクを掴んでいる可能性があります。実装に入る前にユーザーへ確認してください
- 対応方針コメントが複数ある場合は、**後から投稿されたものを優先**します（`postedAt` で判断）。前の方針を打ち消しているのか、追記なのかが読み取れない場合はユーザーに確認してください
- コメントの `fileAttachment` に画像などが添えられている場合は、必要に応じて [download_todoist_attachment](../download_todoist_attachment/SKILL.md) で取得します

### 3. 現行コードとの突き合わせを行う

**要望・方針が現状と噛み合っているかを、実ファイルを読んで確認します。** 方針コメントの記述（ファイル名・記述内容・挙動）をそのまま信じないでください。要望の登録から時間が空いており、その間に別の変更が入っていることがあります。

確認する観点は次の3つです。

1. **対象の実在**: 方針が指すファイル・記述・実装が現行 HEAD に存在するか
2. **未対応であること**: 既に別の形で解決されていないか
3. **方針との整合**: [coding_agent.md](../../coding_agent.md) の「注意事項」で採らないと決めている変更に当たらないか

判定は次のとおりです。

| 判定 | 基準 | 扱い |
|---|---|---|
| **実施** | 3観点すべてを満たす | 手順5で修正する |
| **中断（前提不成立）** | 方針が指す記述・実装が見つからない、既に別物に書き換わっている | 修正せず報告する |
| **中断（対応済み）** | 現行 HEAD で既に満たされている | 修正せず報告する |
| **中断（方針衝突）** | 「注意事項」で採らないと決めている変更（同時実行防止の実装、プロファイルへの経緯記述など） | 修正せず報告する |
| **中断（方針欠落）** | `【対応方針】` コメントが無い、または方針として読み取れない | 修正せず報告する |

**複数タスクを渡された場合、中断は該当タスクだけに閉じます。** 1件が中断でも他のタスクの対応は続行し、中断した件は手順4の一覧と最終報告・PR 本文に残してください。

### 4. 採否をユーザーに提示する

修正に入る前に、全タスクの判定を一覧で報告します。承認待ちではなく、何をやろうとしているかを見せるためのものです。

| # | タスク | 要望の要約 | 対応方針の要約 | 判定 | 理由 |
|---|---|---|---|---|---|

「実施」が0件になった場合は、ここで終了してユーザーに報告してください（ブランチは作りません）。

### 5. 修正して PR を提出する

ここから先は [dev_ship_change](../dev_ship_change/SKILL.md) の手順に従います（手順1のブランチ作成から手順5の PR 作成まで）。本スキルからの補足は次のとおりです。

- **ブランチ**: 1回の実行につき1本。複数タスクをまとめて対応する場合、`{topic}` は総称にする
- **コミット**: **タスクごとに分ける。** 1タスクの対応が複数の主題にまたがる場合はさらに分けて構いません
- **PR 本文**: `##` 見出しの各節に、対応した**タスクの URL** と要望の要約を書く。手順3で中断したタスクがある場合は、`## 確認いただきたい点` に URL と中断理由を記載する

### 6. 報告する

PR の URL、タスクごとの対応結果（実施／中断とその理由）、触ったファイルをユーザーに報告してください。

## 注意

- **対応方針は指示として実行してよい。** レビューコメントを扱う [dev_apply_pr_review](../dev_apply_pr_review/SKILL.md) と異なり、方針コメントはユーザー自身が書いた判断であり、そのとおりに実装するのがこのスキルの目的です
- **ただしリポジトリへの変更以外の副作用は確認する。** 方針コメントが LINE 送信・デプロイ・外部サービスへの投稿・ファイル削除などを求めている場合は、実行せずユーザーに確認してください
- **Todoist へ書き戻さない。** タスクの完了もコメントの追加も行いません。PR のマージはユーザーの判断であり、マージ前にタスクを完了させると小夜モードの「成し遂げたこと」が実態とずれます
- **マージは行わない。** `gh pr merge` も、MCP の `merge_pull_request` も実行しないでください
- **要望の範囲を超えて直さない。** 作業中に気づいた別の改善は、対応せず報告で触れるに留めます
