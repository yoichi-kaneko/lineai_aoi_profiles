# GitHub に投稿する文章の記載ルール

`dev_handle_renovate_pr` と `dev_bundle_renovate_prs` の両方から参照する共通のルールです。手順を変えるときは、両方のスキルから見ても成り立つかを確かめます。どちらかのスキルを廃止するときは、この `shared/` ディレクトリを残る側へ移し、参照しているリンクを書き換えます。

PR のコメントや本文に調査結果を書くときは、次に従います。

- 調査結果は事実と根拠（リリースノートの該当箇所、照合したファイル）を示し、推測は推測と書く。
- 判定は [investigation.md](investigation.md) の「リスクの判定」の基準に従う。
- 外部リポジトリの PR・issue へのリンクや参照は書かない。このリポジトリは公開されているため、コメントや本文に書くと参照先の PR・issue に自動でメンション（タイムラインへの言及）が飛ぶ。次の形はいずれも書かない。
  - `https://github.com/<owner>/<repo>/pull/<番号>` / `.../issues/<番号>` の URL（`/files` や `#issuecomment-...` が付いたもの、Renovate の PR 本文にある `redirect.github.com` 経由のものも含む）
  - `<owner>/<repo>#<番号>` の短縮形
  - リリースノートや CHANGELOG にある `(#1234)` のような番号だけの参照。書き写すとこのリポジトリの PR・issue へのリンクになり、別物を指してしまう
- 根拠は、リリースや compare へのリンクと、リリースノートの該当箇所の見出しや文言で示す。リリース（`.../releases/tag/<タグ>`）や compare（`.../compare/<旧タグ>...<新タグ>`）へのリンクはメンションにならないので書いてよい。
- 同じ理由で、リリースノートにある `@<ユーザー名>` も書き写さない（そのユーザーへのメンションになる）。

## 投稿前の確認

投稿する前に、上で禁じている形が紛れ込んでいないかを次の2つで確かめます。どちらかで何か出力されたら該当箇所を書き直し、両方とも出力が無くなってから投稿します。

```sh
# PR・issue への参照
grep -nE 'github\.com/[^/[:space:]]+/[^/[:space:]]+/(pull|issues)/[0-9]|[[:alnum:]_.-]+/[[:alnum:]_.-]+#[0-9]|(^|[^[:alnum:]_&])#[0-9]' <作業ファイル>
# ユーザーへのメンション
grep -nE '(^|[^[:alnum:]_/])@[A-Za-z0-9_-]+([^/A-Za-z0-9_-]|$)' <作業ファイル>
```

メンションの確認は、npm のスコープ付きパッケージ名（`@scope/name`）と、`next@16.4.5` や `actions/checkout@v7` のような版の指定（`@` の直前が英数字）を検出しません。

`dev_bundle_renovate_prs` は、取り込んだ Renovate PR を本文の表で `#<番号>` と意図して参照します。その場合の確認方法は `dev_bundle_renovate_prs` の手順に書いてあります。

本文はシェルの引数に直接書かず、必ずファイル経由で渡します（改行や記号のエスケープの崩れを避けるため）。
