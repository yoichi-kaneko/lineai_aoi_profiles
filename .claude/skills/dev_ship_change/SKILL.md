# dev_ship_change

このリポジトリへの修正を、**ブランチ作成 → 実装 → コミット → プッシュ → PR 作成**まで一続きで行うための開発用スキルです。

修正内容そのものには関与しません。実装は通常どおり進め、その前後の Git 操作と PR 提出をこのスキルの手順で揃えます。

## 概要

- **対象**: コーディングエージェントモードでの変更作業全般（プロファイルの md 修正・スキル追加・`src/` の実装など）
- **規約の正本**: ブランチ命名・コミット・PR 本文の規約は [dev_git_workflow.md](../../docs/dev_git_workflow.md) を参照する
- **判断基準の正本**: 「その修正を入れるべきか」は [coding_agent.md](../../coding_agent.md) の「注意事項」に従う

## 前提

- `gh` が認証済みであること
- 作業ツリーに、今回の変更と無関係な未コミットの差分が無いこと（ある場合は手順1で確認する）

## Claudeへの指示

### 1. 作業ブランチを用意する

現在の状態を確認します。

```bash
git status --short && git branch --show-current
```

- **`main` にいる場合**: [dev_git_workflow.md](../../docs/dev_git_workflow.md) の命名規約に従ってブランチを作成する

```bash
git checkout -b {種別}/{topic}_$(TZ='JST-9' date +%Y%m%d)
```

- **既に `main` 以外にいる場合**: その作業の続きであればブランチを作らずそのまま使う。別件であれば `main` から切り直すかをユーザーに確認する
- **無関係な未コミットの差分がある場合**: 勝手にコミットせず、扱いをユーザーに確認する

### 2. 修正を実装する

通常のコーディング作業として進めます。このスキルは実装内容に干渉しません。

実装中に「一般的なベストプラクティスだが、このリポジトリの方針と衝突するかもしれない」と感じる変更に行き当たった場合は、[coding_agent.md](../../coding_agent.md) の「注意事項」を確認してください。方針として明示的に採らないことになっている事柄があります。

`.claude/docs/` や `.claude/skills/`、`modes/`、`src/` にファイルを追加・削除した場合は、`.claude/coding_agent.md` と `README.md` のディレクトリ構成の記載も更新します。

### 3. コミットする

論理単位でコミットします。変更が複数の主題にまたがる場合は、無理に1コミットへまとめず分けてください。

メッセージの形式（1行目の要約・本文の書き方・`Co-Authored-By` トレーラー）は [dev_git_workflow.md](../../docs/dev_git_workflow.md) の「コミット」に従います。

`.env` と `tmp/` 配下をステージに含めないでください。

### 4. テストを実行してプッシュする

```bash
pnpm test
```

- 失敗した場合は**プッシュせず**、原因を直してから再実行する。CI（`.github/workflows/test.yml`）が同じコマンドを実行するため、ここで落ちるものは CI でも落ちる
- 今回の変更と無関係な既存の失敗であれば、その旨をユーザーに報告して判断を仰ぐ

通ったらプッシュします。

```bash
git push -u origin $(git branch --show-current)
```

### 5. PR を作成する

本文は複数行の Markdown になるため、シェルに直接書かず**ファイル経由**で渡します。一時ファイルは `tmp/` ではなくスクラッチパッドに置いてください（`tmp/` は碧衣のモードが使う揮発領域のため）。

```bash
gh pr create --title "{タイトル}" --body-file {本文ファイルのパス}
```

タイトル・本文の構成、`## 確認いただきたい点` 節、フッターの扱いは [dev_git_workflow.md](../../docs/dev_git_workflow.md) の「プルリクエスト」に従います。

### 6. 報告する

作成した PR の URL と、変更の要点（触ったファイル・コミットの内訳）をユーザーに報告してください。手順4でテストが失敗した、手順5で PR 作成に失敗したなど、途中で止まった場合はその時点の状態を報告します。

## 注意

- **マージは行わない。** レビューとマージはユーザーの判断です。`gh pr merge` を実行しないでください
- **`main` へ直接プッシュしない。** 手順1のブランチ確認を飛ばさないこと
- 既に同じブランチの PR が存在する場合は、新規作成せずプッシュのみで済みます。`gh pr list --head $(git branch --show-current)` で確認してください

## 他スキルとの役割分担

| スキル | 役割 |
|---|---|
| `dev_ship_change` | 変更の実装から PR 提出まで（このスキル） |
| [`dev_apply_pr_review`](../dev_apply_pr_review/SKILL.md) | 既存 PR のレビュー指摘の検証と修正対応 |
