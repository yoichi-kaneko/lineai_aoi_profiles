# review_image_feedback

碧衣の画像生成について、一定期間に溜まった**画像生成ログ（`image_logs`）**と**ユーザーフィードバック（`image_feedback`）**をまとめてレビューし、`assets/image_guideline.md` の改善につなげるスキルです。issue #43 の柱Cにあたります。

## 前提・思想

- **手動起動・1〜3週間サイクル**: 自動実行はしません。ユーザーが「画像レビューして」等と手動で起動したときだけ動きます。
- **読み手はこのスキルだけ**: `image_logs` / `image_feedback` は日々の各モード（暁・望・小夜・帰灯・調べ・響）のコンテキストに流入しないよう専用コレクションに隔離されています。集計の土台と FB はこのスキルでのみ読み解きます。
- **客観的な土台**: 「似た構図・情景が続いていないか」を主観でなく**集計**で判定します（柱A の [image_logs スキーマ](../../docs/image_log_schema.md) が土台）。
- **human-in-the-loop**: ガイドラインの書き換えは必ず**修正差分案を提示し、ユーザーが承認してから**反映します。勝手に `assets/image_guideline.md` を編集しないでください。
- **「核 / 彩り」2層モデル**: 仕分けと修正方針は `assets/image_guideline.md` セクション1（核＝不変層／彩り＝可変層）に従います。核は安易に動かさず、彩りは積極的に揺らす――この非対称が要です。
- **偏りの二義性（是正すべき偏り／歓迎すべき偏り）**: 彩り層の偏りには2種類あります。①評価の裏付けがない、惰性・自己選択による偏り → 是正して多様性を回復する対象。②ユーザーが好ましいと評価した要素への偏り → むしろ歓迎し、その要素の頻度・重みを意図的に高める対象。本スキルの「補正」は①を均すだけでなく、②を積極的に強める方向も含みます。偏りの数値（ステップ3）だけでは①②を区別できないため、**必ずステップ2の評価と突き合わせて**判断します。

## 使うもの

- 取得: **get_firestore_docs** スキル（`--collection` で専用コレクションを指定）
- 画像の現物確認（任意）: **download_image** スキル（`image_logs` の `cloudinary_url` を `tmp/` に保存して内容を参照）
- 設定資料画像の確認（任意）: **Read** ツールで `assets/images/` 配下の該当 PNG（base.png / outfit_*.png / room_*.png / ruri.png / hotaru.png / urushi.png）を直接読み込む。索引はガイドライン セクション5。
- 修正要望の記録: **put_todoist_task** スキル ― 設定資料画像そのものへの修正要望（ステップ6）を Todoist タスクとして残す（内容確認・返信・完了の管理がしやすいため）
- マーカー記録: **put_firestore_doc** スキル（`--collection image_feedback_reviews`）
- 参照: [image_logs スキーマ](../../docs/image_log_schema.md) / [image_feedback スキーマ](../../docs/image_feedback_schema.md) / [画像生成ガイドライン](../../../assets/image_guideline.md)

## 手順

### ステップ0：レビュー対象期間の決定

1. **前回マーカーの参照**: `image_feedback_reviews` コレクションから直近のレビューマーカーを探します。広めの窓（例：今日から遡って90日）で取得し、`date` が最新のドキュメントを選びます。

   ```bash
   cd {プロジェクトルートの絶対パス}
   pnpm exec tsx src/firebase/get_docs.ts "{90日前}" "{今日}" --collection image_feedback_reviews
   ```

   - マーカーの `date` は**レビュー実施日ではなく締め切り位置（`period_to`）**であり、実施日より手前に記録されます（下記3）。窓の中に見つからない場合は、初回と決めつけず**窓をさらに広げて**探し直してください。`image_logs` の最も古いドキュメントの日付まで遡って探し、そこまでで1件も見つからなければ初回レビューと判断します。

2. **取得期間（dateFrom 〜 dateTo）を決める**:
   - **dateTo** = 今日（JST）。これは**取得の上限**であり、レビューを締め切る日ではありません。
   - **dateFrom** = 直近マーカーの `description.period_to` の翌日。
   - マーカーが1件も無い（初回レビュー）場合は、`image_logs` の最も古いドキュメントの日付を dateFrom にするか、ユーザーに開始日を尋ねてください。

3. **締め切り位置（`period_to`）は取得期間の末日ではありません**。マーカーに記録して次サイクルの起点になる `period_to` は、**評価が届いている連続区間の末尾**まで手前に戻します（決め方はステップ7）。集計・分析（ステップ2〜3）は取得期間の全件で行い、締め切り位置だけを手前に置く形です。

   > **なぜレビュー実施日で締めないか**: `image_feedback` は**評価対象画像の日付**で保存されます（`評価 <YYYY-MM-DD> ...` と明示した場合はその日付。[image_feedback スキーマ](../../docs/image_feedback_schema.md)）。実施日で締めると、まだ評価を書けていない直近の画像がその場で閉じられ、後日その日付で評価を書いても次サイクルの取得範囲（`period_to` の翌日以降）から外れるため、**二度と集計されません**。評価が届いた所までで締めれば、未評価の区間はそのまま次サイクルへ持ち越されます。

4. 決めた取得期間をユーザーに一言示してから次へ進みます（例：「2026-06-01〜2026-06-21 を対象にレビューします」）。

### ステップ1：image_logs と image_feedback の取得

対象期間で両コレクションを取得し、あわせて綴葉モードを実行した日を洗い出します。

```bash
cd {プロジェクトルートの絶対パス}
pnpm exec tsx src/firebase/get_docs.ts "{dateFrom}" "{dateTo}" --collection image_logs
pnpm exec tsx src/firebase/get_docs.ts "{dateFrom}" "{dateTo}" --collection image_feedback
pnpm exec tsx src/firebase/get_docs.ts "{dateFrom}" "{dateTo}" --type "scribe_handover"
```

- 各ドキュメントの `description` は JSON 文字列です。パースして構造化データとして扱ってください（スキーマは上記スキーマ docを参照）。
- **3本目（`scribe_handover`）は綴葉モードの実行日を知るためのものです**。綴葉モードの SNS レポート画像は `image_logs` に記録されず**評価対象外**ですが（理由は [image_logs スキーマ](../../docs/image_log_schema.md) の「綴葉モードの画像を対象外とする理由」）、綴葉実行日はユーザーへ画像が2枚届きます。ログに残らない一枚がある日を知らないと、レポート画像への評価を小夜の一枚へ誤って紐付けてしまうため、**日付の一覧だけを控えておきます**（本文の内容はこのスキルでは読みません）。取得できなかった場合は、綴葉日が不明である旨をステップ2の注記に残してください。
- **実際の画像を見たいとき**: `image_logs` の `description.cloudinary_url`（[image_logs スキーマ](../../docs/image_log_schema.md)参照）には、生成・送信した画像の公開 URL が入っています。ラベル（`shot_size` などの正規化値）だけでは判断しづらい指摘（例：「背景が寂しい」「顔が前と違う」）を検証したいときは、**download_image** スキルでその URL を `tmp/` にダウンロードし、画像の中身を参照してください。認証不要の公開 URL なので、そのまま取得できます。なお偏り集計（ステップ3）は正規化ラベルだけで足りるため、現物確認は限られた枚数に絞って構いません。選定の目安は次の通りです。
  - **確認する**: ステップ2で**複数回**現れた懸念（例：「背景が寂しい」が3件）。代表として該当 `target_date` の画像を**2〜3枚**ほど見て、ラベルに表れない共通要因がないか確かめます。
  - **確認しなくてよい**: 1回だけの指摘、`shot_size` などラベルで既に裏が取れる指摘、`kind=rating` のスコアだけで傾向が明らかなもの。
  - 複数種類の懸念が併存する場合も、現物確認は1サイクルあたり**合計5枚程度まで**を目安に、優先度の高い懸念から絞り込んでください。
- どちらかが空でも処理は続行します（ログだけ／FBだけのレビューも成立します）。両方空なら、その旨を伝えて終了します（マーカーは更新しない）。
- 取得件数（image_logs の N、image_feedback の件数）を控えておきます。

### ステップ2：個別評価の集約（image_feedback / kind=rating）

`kind` が `rating` のフィードバックを集約します。

- **前回マーカーがある場合**: 前回の `reviewed_at`（無ければマーカーの Firestore `createdAt`）より前に作成されたフィードバックは既処理です。文面の参考にはしてよいですが、称賛／懸念の「繰り返し」件数・ガイドライン修正・Todoist 登録の根拠には使いません（詳細はステップ7）。
- **スコア分布**: 1〜5 の各点の件数と平均（`score` が null のものは「スコアなし」として別カウント）。
- **称賛点 / 懸念点の抽出**: `comment` を読み、**繰り返し現れるポジティブ要素**（例：「ルリが可愛い」「夜の情景がよい」）と**繰り返し現れる懸念**（例：「背景が寂しい」「顔が前と違う」）を、件数とともに箇条書きで列挙します。1回だけの指摘も拾いますが、複数回現れたものを優先度高として扱います。
#### 評価対象の画像との突き合わせ

同じ日に複数枚を届けた日（響モードの個別生成と、その日の小夜モードの一枚など）があるため、日付だけでは一意に決まりません。一方で `image_id` は `{モード名}-{HHMM}` 形式で**日付を含まないため、ID単体でも対象期間内で一意になりません**（別日の同じモード・同じ時刻が同じ値になります）。したがって**照合の鍵は `(対象日, image_id)` の組**です。どちらか一方だけで「最も確かな紐付け」と判断しないでください。

**1. 対象日を決める**

- `target_date` があればその日付を対象日とします。
- 無ければ、保存された `date`（投稿日）を対象日とします（遅延返信時のずれは既知の近似です。[image_feedback スキーマ](../../docs/image_feedback_schema.md)）。

**2. 対象日の `image_logs` から候補を絞る**

- **`target_image_id` があるコメント**: 対象日のログのうち、次のいずれかで一致するものを候補とします。
  - **完全一致**: `image_id` が `target_image_id` と同一のもの（例：`#night-2210` → `night-2210`）。
  - **モード名の略記**: `target_image_id` が `night` / `off_mountain` / `talk` のいずれか（モード名のみ）の場合は、`mode` が一致するログを候補とします。ユーザーが `{HHMM}` を書き写さずに `#night` と名指しできるようにするための略記です（[image_logs スキーマ](../../docs/image_log_schema.md) の「画像の識別子（`image_id`）」）。
  - 完全一致の候補が1件でも見つかった場合は、略記としての解釈は行いません（完全一致を優先します）。
- **`target_image_id` が無いコメント**: 対象日のログすべてを候補とします。

**3. 候補の件数で分岐する（0件・1件・複数件を必ず明示的に扱う）**

| 候補 | 扱い |
|---|---|
| **1件** | その1枚へ紐付けます。構図・情景のラベルと突き合わせて称賛点／懸念点を読み解きます |
| **0件** | 紐付けません。対象期間外の画像への評価、綴葉の画像への評価、識別子の書き間違いなどが該当します |
| **複数件** | 紐付けません。**恣意的に1枚を選ばないでください**（`createdAt` が早い方を採る、`talk` を優先する等の推測もしないこと） |

- 紐付かなかった評価は「**対象が曖昧な評価**」として、**コメントの内容だけ**を称賛点／懸念点の抽出に使い、構図・情景との紐付けは行いません。
- **同日に複数の `talk` 画像がある日にモード名の略記が使われた場合**は、候補が複数件となるため曖昧扱いになります。これは略記を受け入れる代わりの割り切りであり、異常ではありません。その日を名指しで評価したい場合は完全形（`#talk-2135`）を使う、と案内する材料になります。

**4. 綴葉モードの実行日は、宛先未指定の評価を紐付けない（誤帰属の防止）**

綴葉実行日はユーザーへ画像が2枚届く一方（綴葉の通知画像と小夜の一枚）、`image_logs` には小夜の1件しか残りません。そのため上記3で「候補1件」となり、**レポート画像への評価が小夜の一枚へ確信を持って誤帰属します**。これを防ぐため、次のとおり扱ってください。

- 対象日がステップ1で洗い出した **`scribe_handover` の日付に当たる場合、`target_image_id` が無いコメントは、候補が1件であっても紐付けず、対象が曖昧な評価として扱ってください**。
- **`target_image_id` で名指しされている場合は通常どおり紐付けます**（モード名の略記を含む）。`#night` と書かれていれば対象は明確であり、綴葉日であっても曖昧にする理由はありません。
- 綴葉日由来の曖昧分は、下記6のとおり**内訳として件数を分けて控えてください**。

**5. 日内の並び順に依拠する判断はしない**

- 同じ日のログを時系列に並べる必要が生じた場合、順序は **`createdAt` の昇順**とします。`get_firestore_docs` は `date` の範囲指定のみで取得し `orderBy` を持たず、`date` は日付の 0 時で同一値になるため、**返却順は日内では時系列になりません**（以降はドキュメントIDの順です）。並び順に触れるときは必ず `createdAt` で並べ直してください。
- ただし、**並び順を使って評価の対象を決めてはいけません**。ユーザーへ届いた枚数と `image_logs` の件数は必ずしも一致しないため（綴葉の画像は記録されず、LINE 送信に失敗した画像は記録されるが届きません）、「その日の何枚目か」で対象を特定すると静かに1つずれます。`createdAt` の並びは、報告の中で時系列を示すときにだけ使ってください。

**6. 曖昧扱いになった件数を控える**

- **対象が曖昧な評価の総件数**を控えておいてください。これが多い場合は、識別子の案内が届いていないシグナルであり、ステップ6の要望として挙げる材料になります。
- 内訳として、**綴葉実行日によるもの**（上記4）と、**それ以外**（候補0件・複数件）を分けて控えてください。前者が多ければ案内すべきは「綴葉日には `#night` を添える」であり、後者が多ければ案内すべきは識別子そのものの使い方です。要望の書き分けに使います。

### ステップ3：構図ログの偏り集計（image_logs）― 機械集計

`image_logs` の各ドキュメントを、以下のフィールドごとに**値の出現回数を数えて分布表**を作ります。表記揺れはスキーマの正規化値（英語スネークケース）で揃っている前提です。

集計対象フィールド: `shot_size` / `camera_direction` / `outfit` / `scene_category` / `time_of_day` / `companions`（companions は配列。ルリのみ・蛍のみ・漆のみ・ルリ＋蛍・ルリ＋漆・なし の6区分で数える。`["hotaru","urushi"]` など設計上存在しない組み合わせは区分に入れず別途報告する）。

**ユーザーが指定した可変要素は、偏り集計から切り分けてください。** `image_logs` の `user_specified`（[image_logs スキーマ](../../docs/image_log_schema.md)）は、ユーザーが依頼で明示的に指定した可変要素のキー名です（響モードの「ルリと一緒に」など）。指定に従った結果は**碧衣の自己選択による偏りではない**ため、惰性の偏りと同じ土俵で数えると誤った是正提案につながります。

- **各軸の偏り判定は、その軸が `user_specified` に含まれないログだけで行ってください**（例：`companions` の分布は、`user_specified` に `companions` を含むログを除いた集合で数える）。除外は軸ごとに行い、ログ全体を除外しないでください（1軸だけ指定された依頼でも、他の軸は通常どおり抽選されているためです）。この除外後の件数をその軸の有効件数 `N_axis` とします。
- **指定された分は別表として控えます**。どの軸が何件指定されたか、指定の結果どの値が採られたかを一覧にしてください。ユーザーが繰り返し同じ要素を指定しているなら、それは「歓迎すべき偏り」の候補（前提・思想の「偏りの二義性」）であり、ステップ4・5で重みテーブルへ反映する材料になります。
- **`mode` 別の内訳も控えてください**（`night` / `off_mountain` / `talk`）。`talk` は依頼に応じた個別生成のため、定期生成（`night` / `off_mountain`）とは分布の性質が異なります。N が十分あるなら、`talk` を除いた集計も併記すると、定期生成の偏りが見やすくなります。

各フィールドについて、値・件数・割合（件数 / `N_axis`）を表で示します。全体のログ件数 N を分母にしないでください。`N_axis` が 0 の軸は**判定対象なし**として扱い、偏りフラグも立てません。そのうえで**偏りフラグ**を立てます（既定ルール。`N_axis` が小さいときは弱いシグナルとして注記）:

- **過剰**: 単一の値が **40% 以上**、または上位2値の合計が **70% 以上**。
- **欠落（random_choice 軸のみ）**: `shot_size` / `camera_direction` で、語彙表（ガイドライン セクション8③）にあるのに**1サイクルを通して1度も選ばれていない値**。
- **意図的な重み付けの扱い（条件別）**: 上記の閾値は**一様抽選を前提とした目安**です。重みテーブルの値は**条件に該当する抽選でのみ**出現率が上がる設計なので、除外・注記も**全体集計ではなく、その行の条件に合うログの部分集合**で行ってください。
  - **条件マッチの切り出し**: 重みテーブルの各行について、その条件に該当しそうな `image_logs` を抽出します。構造化フィールドで足りる部分（例：山行シーン → `scene_category` が `hike`）はそれで絞り、尾根・稜線・展望など条件の細部は `prompt_digest` を手がかりにベストエフォートで判定します（厳密一致は求めません）。
  - **条件内の比較**: 部分集合内で該当軸（例：`shot_size`）の実測分布を出し、重み適用時の**実効確率の目安**（ガイドライン表の値）と比較します。実測が設計値の近傍なら「重み付けによる想定内の偏り」と注記し、過剰フラグの対象外とします。実測が設計値を大きく超える場合は、重み値そのものが強すぎないかをステップ4・5で見直す材料にします。
  - **全体集計との切り分け**: 条件外のログでは一様抽選が既定なので、重み付き値の**全体出現率**が高いことだけでは除外しません。全体で過剰に見えても、条件マッチ分で説明できるなら想定内、条件外まで偏っているなら従来どおりの偏りシグナルとして扱います。
  - **サンプル不足**: 条件マッチ件数が少ない（目安: 3 未満）ときは、条件別比較は参考扱いに留め、その旨を明記します。重みテーブルに載っていない軸・値の偏りは従来どおり全体集計で判定します。
- **`companions` の扱い（シーン条件付きの重み付け軸）**: ルリとデジタル上の友人（蛍・漆）の登場可否は、ガイドライン セクション6・7で **`random_choice` の重み付き抽選**と定められています。`hike` 以外ではルリ（`ruri:4 none:1`）と友人（`hotaru:2 urushi:1 none:7` の三択を1回）を独立に抽選し、`hike` では友人を抽選対象外としてルリのみを抽選します。友人の抽選が三択であるため、**蛍と漆が同時に登場する組み合わせは設計上存在しません**。設計上の期待分布は次のとおりです。
  - `hike` 以外: ルリのみ 56% / ルリ＋蛍 16% / なし 14% / ルリ＋漆 8% / 蛍のみ 4% / 漆のみ 2%
  - `hike`: ルリのみ 80% / なし 20%

  したがって、上記の**過剰フラグ（40%）・欠落フラグは `companions` には適用しません**。`scene_category` が `hike` のログとそれ以外に分けたうえで、実測分布を設計値と突き合わせ、乖離の大きさで判断してください。設計値から大きく外れる場合（例：`hike` 以外が十分な件数あるのに友人が1件も出ていない、ルリが全件に登場している）は、抽選が実施されていない可能性を含めて注記します。なお蛍単独（4%）・漆単独（2%）・ルリ＋漆（8%）は設計上もともと稀なため、出現0でも件数が少ないうちは偏りシグナルとして扱いません。逆に `["hotaru","urushi"]` のように蛍と漆が同居するログが現れた場合は、三択の抽選が正しく引かれていないシグナルとして報告してください。
- **構図2軸の再抽選ログの扱い**: `shot_size_rerolled_from` / `shot_size_reroll_reason` / `camera_direction_rerolled_from` / `camera_direction_reroll_reason`（[image_logs スキーマ](../../docs/image_log_schema.md)）は、ガイドライン セクション8③の **構図軸の再抽選ログ** に従った記録です（任意キーで、再抽選が無かった日は存在しません）。シーンとの噛み合わせによる選び直しと、**抽選した2軸の成立チェック** によるショットサイズの引き直しの両方を含みます。
  - **分布表は `shot_size` / `camera_direction` の採用値だけで数えます**。`*_rerolled_from` の値を分布へ足し込まないでください（実際にその構図で描いていないため）。
  - 再抽選キーが付いたログの件数と、除外された値・もう一方の軸との組み合わせは**別表として控えておきます**。特定の組み合わせ（例：`over_the_shoulder` × `knee_shot`）で再抽選が繰り返されているなら、語彙表の説明の補強や重みテーブルの見直しをステップ5の提案材料にしてください。
  - `*_reroll_reason` が許可された理由（シーンとの噛み合わせ、2軸どうしの成立性）の説明になっておらず、好みや描きやすさを理由にしていると読めるものが続く場合は、抽選制の趣旨（自己選択による偏りの打ち消し）が緩んでいるシグナルとして報告に含めます。
- **`codex_review` の扱い（分布軸ではなくクロス集計の材料）**: `codex_review`（[image_logs スキーマ](../../docs/image_log_schema.md)）は、プロンプトを外部レビュー（[codexレビュー](../../docs/codex_review.md)）に通した結果です。抽選軸ではないため**偏りフラグの対象にしません**。フィールドがあるログについては件数の内訳（`applied` / `not_applied` / `no_findings` / `skipped`）だけを控え、次の点に使ってください。
  - **未記録（フィールド欠落）の扱い**: 導入前の旧ログなど `codex_review` キー自体が無い記録は、4値のいずれにも入れず**未記録**として件数を別途控えます。`skipped`（レビュー工程は動いたが実行されなかった）と混同しないでください。未記録は `skipped` の判定・件数・割合の分母からも除外します。
  - **ステップ2の評価との突き合わせ**: 構図やオブジェクトの位置関係に関する指摘（「何を描いているか分かりにくい」「アングルが不自然」など）が、`skipped` のログに偏って出ていないか。偏っているならレビュー工程が効いているシグナルであり、`skipped` の原因（codex の未導入・認証切れ・時間切れ）の解消をステップ6の要望として挙げる材料になります。
  - **`skipped` が大半を占める場合**: レビュー工程が実質的に動いていない状態です（未記録を除いたうえで判定）。分布集計への影響はありませんが、その旨を報告に明記してください。
- **主役は `shot_size` と `camera_direction`**（`random_choice` で抽選＝彩りが本当に多様かを測る軸）。`outfit` / `scene_category` / `time_of_day` の偏りは生活実態を反映するため、偏っていても直ちに問題ではありません（情報として提示）。`companions` も抽選軸ですが、既定でルリに寄せた重み付けがあるため、上記の設計値比較で扱います。
- N（image_logs 件数）が **7 未満**のときは、サンプルが小さい旨を明記し、偏り判定は参考扱いにします。
- **偏りフラグは「是正命令」ではなく「要確認シグナル」**: 過剰フラグが立った値でも、ステップ2でその要素が繰り返し称賛されていれば「歓迎すべき偏り」であり、是正せず**むしろ伸ばす**候補とします（前提・思想の「偏りの二義性」）。称賛の裏付けがなく惰性で偏っているものだけを是正対象とします。いずれかは必ずステップ2の評価と突き合わせて判定してください（構図2軸 `shot_size` / `camera_direction` を重み付けで調整する場合の作法は、ステップ4の注釈を参照）。

「似た構図が続いている」というFB（傾向／個別）があれば、この分布表が**客観的な裏付け**になります。両者を突き合わせて言及してください。

### ステップ4：「核 / 彩り」仕分け

ステップ2の評価・ステップ3の偏りを、`assets/image_guideline.md` セクション1の二層へ仕分けます。

- **核への指摘**（キャラクター同一性・品質の床・ラベル文字混入など。例：「顔が前回と違う」「線が荒い」「ラベルが写り込んだ」）→ 核を**締める**方向。
- **彩りへの指摘**（構図・情景・衣装・時間帯の偏りや、もっと自由に等）→ 彩りの配分を調整する方向。調整には2方向があります。
  - **広げる**（多様性の回復）：評価の裏付けがなく惰性で偏った値の重みを下げる／語彙を追加する。例：「バストアップ正面が続く」「もっと大胆な構図を」。
  - **寄せる**（好ましい偏りの強化）：称賛が繰り返された要素の頻度・重みを上げ、優先的に選ばれるようにする。例：「夜の情景がよい」が複数件 → `time_of_day` で夜を優先候補に。「ルリが可愛い」が複数件 → ガイドライン セクション6の抽選の重み（既定 `ruri:4 none:1`）を引き上げる。
  - **構図2軸（`shot_size` / `camera_direction`）の扱い（注釈）**:
    - この2軸は `random_choice` による**抽選制を維持**します。したがって「寄せる（偏り強化）」は、特定の構図を名指しで指定させたり語彙を削ったりする形ではなく、**ガイドライン セクション8③の重みテーブル**を通じて行ってください。この2軸で許容される編集操作は次の3つです。
      - **一様抽選 → 重み付け抽選への変更**: 重みテーブルに行（条件・軸・値・重み）を追加する。
      - **重みの調整**: 既存行の重みを増減する。
      - **重み付け抽選 → 一様抽選への復帰**: 称賛の裏付けが続かなくなった行を削除する。
    - **条件付きで設計する**: 重みテーブルの行には**適用条件を必ず明示**し、条件に該当するときだけ `--weighted` を使います（例：「稜線・尾根を強調できる山行シーン」でのみ `wide_shot` の重みを上げる）。条件外は一様抽選が既定です。条件なしの全面的な重み付けは許可しません。
    - **重み0は使いません**（どの値も引かれ得る状態を保つことが抽選制の前提）。語彙そのものを外したい場合は、重みではなく語彙表の見直しとして扱ってください。
    - なお「広げる」方向（惰性で過剰な値があるとき、欠落値が選ばれやすくなるよう語彙・説明を補強する等）は、従来どおり扱って構いません。
  - **`companions`（ルリ・友人の登場可否）の扱い（注釈）**:
    - この軸も `random_choice` による**抽選制を維持**します。「寄せる」「広げる」のどちらも、ガイドライン **セクション6・7に記された重みの数値を増減する**形で提案してください（例：ルリの称賛が続く → `ruri:4 none:1` を `ruri:5 none:1` へ。漆の登場が少なすぎるという評価が続く → `hotaru:2 urushi:1 none:7` を `hotaru:2 urushi:2 none:6` へ）。「ルリを毎回登場させる」のように抽選そのものを外す提案は行いません。
    - **友人の三択（`hotaru` / `urushi` / `none`）は1本の抽選として維持します**。蛍と漆を別々の抽選へ分ける（＝二人が同時に登場し得るようにする）提案は、重みの調整ではなくキャラクター設定の変更に当たるため、集計からは行わずユーザーに提起してください。
    - **重み0は使いません**（構図2軸と同じ）。ルリ・蛍・漆のいずれも、引かれ得る状態を保ちます。
    - **山岳・自然シーンで友人（蛍・漆）を抽選対象外とする扱いは、重みの調整対象ではありません**。これは二人の活動領域がデジタル／都市空間に限られるという世界観上の制約（ガイドライン セクション7）であり、評価の集計で動かすものではありません。見直しが必要と判断した場合は、重みの調整ではなくキャラクター設定の変更としてユーザーに提起してください。
- **衝突判定ルール（このスキルが正本）**: 2つのFBが本当に矛盾するのは**同じ層の同じ属性**を指すときだけです。「顔が違う（核）」と「同じ構図（彩り）」は別層なので両立し、両方対応します。「安定して描いて」（核）と「自由に描いて」（彩り）も、別の層を指している限り矛盾しません。矛盾が生じるのは「正面を基本に」対「正面が多すぎる」のように**同じ彩りの同じ属性**へ相反要望が当たったときだけで、その場合のみ、どちらを採るか／配分をどう取るかの判断ポイントとして明示します。
- **テキストで直せない指摘の退避（ステップ5 vs ステップ6 の判定）**: 仕分けの過程で、以下の順で判定し、ステップ5で届かない指摘はステップ6候補として控えます。
  1. **まずステップ5で吸収できるか検討する**: ガイドラインの語彙追加・ウェイト変更・説明の補強（例：`scene_category` や `time_of_day` の語彙拡張、`shot_size` の配分調整）で指摘に応えられるかを考えます。
  2. **該当する設定資料画像を Read で確認する**: ガイドライン セクション5の索引を手がかりに、指摘に関係しそうな `assets/images/` 配下の PNG を Read で直接読み込み、**既存リソースで実現可能か**を判定します。
  3. **判定の切り分け**:
     - **ステップ5に含める**: 資料は足りているが、ガイドラインの彩り層（語彙・ウェイト・説明）を変えればバリエーションや表現を広げられる場合。例：「背景が寂しい」が複数件 → `scene_category` の語彙追加や抽選ウェイトの見直しで多様化できる。
     - **ステップ6に送る**: 資料ファイルそのものの追加・改修が必要な場合。例：`outfit_*.png` に夜のシーン用コーデが存在しない、base.png の表情集に同一性の基準となる顔が無い、ruri.png のゴーグルや尾羽が伝わりにくい等。
  ここでは最終的な記録は行わず、ステップ6候補として控えるところまでで構いません（詳細な確認と記録はステップ6で行います）。

### ステップ5：ガイドライン修正差分案の提示（承認 → 反映）

仕分け結果をもとに、`assets/image_guideline.md` への**具体的な修正差分案**を作り、ユーザーに提示します。

- どのセクション（核 or 彩りのどの項目）を、**どう変える**かを before/after で示します。例：
  - 彩りの調整（広げる）：惰性で偏った値の重みを下げる／語彙を追加する旨をセクション8③に追記。
  - 彩りの調整（寄せる）：称賛された値を優先・増頻する旨を該当セクションに追記。例：夜の情景の称賛が続けば「8④」で夜の時間帯を優先候補にする。※構図2軸（`shot_size` / `camera_direction`）は、セクション8③の**重みテーブルの行追加・重みの増減・行の削除**という形で提案してください。`companions`（ルリ・友人の登場可否）は、セクション6・7に記された**重みの数値の増減**という形で提案してください（例：ルリの称賛が続けば `ruri:4 none:1` を `ruri:5 none:1` へ）。いずれもステップ4の注釈を参照。before/after では、変更後の実効確率の目安も添えます。
  - 核の引き締め：混入したラベル文字対策の文言を末尾注意文（セクション8⑤）に補強。
- 各案には**根拠**（ステップ2の評価件数・ステップ3の分布数値）を添えます。
- **ユーザーが承認した項目だけ** `assets/image_guideline.md` を Edit で反映します。未承認・保留の項目は反映しません。何も承認されなければガイドラインは変更しません。
- ここで扱うのは**文言（テキスト）で是正できる**修正だけです。原因が `assets/images/` の設定資料画像そのものにあると判断した指摘は、文言を直しても解決しないため、次のステップ6で Todoist タスクとして記録します。

### ステップ6：設定資料画像（assets/images）への修正要望の記録

ステップ2の評価・ステップ4の仕分けで、原因が `assets/image_guideline.md` の**文言ではなく設定資料画像そのもの**（`assets/images/` 配下の PNG）にあると判断した指摘を、ここで扱います。設定資料画像は碧衣が直接編集できないため、修正そのものは行わず、**「どう直されるとよいと感じたか」を Todoist タスクとして残し**、後日に資料を管理するユーザーが内容を確認・対応し、完了管理できるようにします。資料側の修正要望が何も無ければ、このステップはスキップします（タスクは作りません）。

> Firestore ではなく Todoist に残すのは、設定資料画像の修正要望が「内容を確認し、対応し、完了させる」性質のタスクであり、状態管理・返信・完了チェックは Todoist の方が扱いやすいためです。

1. **該当資料の確認**: ガイドライン セクション5（参考資料の索引）を手がかりに、対象の設定資料画像を **Read** ツールで直接読み込み、FB の指摘が資料のどこに由来するかを確かめます。`assets/images/` 配下の PNG は Read でそのまま画像として読めます（ダウンロード不要）。
   - 例：「顔が前回と違う」が複数件 → base.png の表情集・顔の基準を確認。「ゴーグルが分かりづらい」→ ruri.png を確認。「望むコーデが無い」→ 該当 outfit_*.png を確認。
   - 確認の結果、文言（ガイドライン）側で吸収できると分かった場合はステップ5に戻し、ここでは記録しません。資料そのものの修正が望ましいと判断したものだけを次へ進めます。

2. **修正要望の記録（put_todoist_task）**: 対象資料ごとに、**put_todoist_task** スキルで Todoist にタスクを1件作成します。一目で要望と分かるよう、タイトルに対象資料名を含めてください。
   - **content（タイトル）の目安**: `[画像要望] base.png：顔の同一性の基準を追加` のように、`[画像要望]` プレフィックス＋対象資料名＋要望の要約。
   - **description（詳細）の目安**: 現状の懸念（FB の根拠・件数）、どう直されるとよいか、根拠となった対象日などを記載します。詳細は引数で直接渡せないため、本文を `tmp/todoist_task.txt` に Write で書き出し、`--description-file` で渡してください（改行はそのまま改行として書けばよく、`\n` への置換は不要です）。

   `tmp/todoist_task.txt` の例:

   ```text
   懸念: 「顔が前回と違う」という指摘が3件。表情集の中で同一性の基準となる顔が読み取りづらい可能性。
   要望: 正面・無表情の基準カットを1点、顔の同一性が分かりやすい形で追加してほしい。
   根拠: feedback 3件 / 対象日 2026-06-05, 2026-06-11
   ```

   ```bash
   cd {プロジェクトルートの絶対パス}
   pnpm exec tsx src/todoist/put_task.ts "[画像要望] base.png：顔の同一性の基準を追加" --description-file tmp/todoist_task.txt
   ```

   > **注意**: 対象資料ごとにタスクを分ける場合、`tmp/todoist_task.txt` は毎回 Write で上書きしてから1件ずつ作成してください（同じ詳細が別のタスクへ紛れ込むのを防ぐため）。

   - 対象資料が複数に分かれる場合は、ファイル単位で複数件のタスクに分けて作成して構いません。

3. 作成したタスク（対象資料・タスクタイトル・件数）を控え、最終報告とステップ7のマーカーに反映します。

### ステップ7：レビュー区切りマーカーの記録

次サイクルの起点を残すため、`image_feedback_reviews` コレクションにマーカーを1件記録します。

#### 締め切り位置（`period_to`）の決め方

`period_to` は**取得期間の末日（今日）ではなく、評価が届いている連続区間の末尾**です。次の順で決めます。

1. **判定に使う評価を選ぶ**: **ステップ2で特定の1枚へ紐付いた `rating`** だけを使います。ステップ2で「対象が曖昧な評価」となったもの（候補が0件・複数件、綴葉実行日の宛先未指定）と、`kind` が `trend` のものは**判定から除外します**。対象日さえ合えば1件で日を閉じる扱いにすると、綴葉のレポート画像や同じ日の別の一枚への評価で締め切り位置が進み、未評価のまま閉じた画像への後日の評価を取りこぼすためです。
2. **`image_logs` のある日を古い順に並べる**: dateFrom から dateTo までのうち、`image_logs` が1件以上ある日付だけを並べます。画像が無い日は判定の対象外で、未評価日としては扱いません。
3. **最初の未評価日で止める**: 並べた日付を古い順に見て、**その日の `image_logs` のうち1枚でも紐付いた評価が無いもの**が残っている最初の日を「最初の未評価日」とします（同じ日に複数枚ある日は、**その日の全ての画像に紐付いた評価があるとき**だけ評価済みです）。その手前までが確定範囲です。
4. **`period_to` = 確定範囲の最後の `image_logs` の日付**とします。未評価日が1つも無い場合も、`image_logs` の最新日をそのまま `period_to` とします（今日の画像がまだ生成されていない時間帯に、その一枚を巻き込んで閉じないため）。
5. **確定範囲が空になる場合**（最初の画像の日から未評価）は `period_to` が前回マーカーから進みません。この場合は**マーカーを記録しません**。レビュー自体は実施して構いませんが、報告で「区切りは据え置き」であることと最初の未評価日を伝えてください。
6. `image_logs` が取得期間に1件も無い場合も、**マーカーを記録しません**。閉じるべき画像は無い一方、今日の一枚がこの後に生成されると、実施日で閉じた場合にその一枚が次サイクルの取得範囲から外れてしまうためです。
7. **解消の見込みが無い未評価日への逃げ道**: 綴葉実行日の宛先未指定など、後から紐付けようがない理由で未評価日が動かせない場合があります。この場合は勝手に飛び越さず、**その日を評価済みとみなして進めてよいかユーザーに確認**し、承認された場合のみ次の日へ進めてください（何サイクルも同じ日で止まり続けないための逃げ道です）。

例：取得期間 2026-08-20〜2026-09-08、`image_logs` は 8/20〜9/07 に存在し、評価は 8/20〜8/30 の分だけ届いている → 最初の未評価日は 8/31 なので `period_to` は **2026-08-30**。次サイクルは 8/31 から始まり、8/31〜9/07 の画像には評価を書く機会が残ります。

> **確定範囲より後のログは、次サイクルでも再び集計されます**。これは二重計上の事故ではなく、評価が揃ってから偏りを判断し直すための意図的な重複です。`summary` に確定範囲を書き添えておくと、次サイクルで重複分を見分けやすくなります。
>
> ただし、**「複数サイクル連続の偏り」の判定に、この重複分を独立した観測として数えないでください**。前サイクルのマーカーの `analyzed_to` 以前のログは前回すでに見たものであり、同じ画像が2サイクルに跨って現れているだけです。連続の偏りとして扱うのは、前回の `analyzed_to` より後に生成されたログに現れた傾向だけとします（`analyzed_to` を持たない旧マーカーでは `period_to` を代わりに使います）。
>
> **フィードバックの再適用はログの再集計と分けてください**。最初の未評価日より後にすでに評価がある場合、そのフィードバックも取得期間に含まれて今回のステップ2〜6で見ていますが、`period_to` は手前に残るため次サイクルでも再取得されます。ログの意図的な再分析とは異なり、**ガイドライン修正（ステップ4〜5）と Todoist 登録（ステップ6）に、前回レビューですでに見たフィードバックを再適用しない**でください。見分け方は、前回マーカーの `reviewed_at`（無ければマーカーの Firestore `createdAt`）より前に作成されたフィードバックを既処理とし、それ以降に届いたものだけを新規適用の根拠にします。既処理分の文面を集約の参考に読むのは構いませんが、「繰り返し」の件数やタスク作成の根拠には新規分だけを使います。

#### マーカーの記録

1. マーカー本文（JSON）を `tmp/firestore_doc.txt` に Write で書き出す（put_firestore_doc の作法）。スキーマ:

   ```json
   {
     "period_from": "2026-06-01",
     "period_to": "2026-06-21",
     "analyzed_to": "2026-06-25",
     "reviewed_at": "2026-06-25T21:30:00+09:00",
     "image_log_count": 18,
     "feedback_count": 5,
     "guideline_updated": true,
     "asset_requests": 1,
     "summary": "正面バストアップ過多を是正。背景の寂しさ指摘を彩りで対応。核は変更なし。base.png の顔基準を1件 asset_requests に登録。6/22〜6/25 は未評価のため次サイクルへ持ち越し。"
   }
   ```

   - `period_to` は上記の締め切り位置です。`analyzed_to` には**今回実際に集計した取得期間の末日（dateTo）**を入れます。両者が一致する場合も省略せず記録してください（「どこまで見て、どこで締めたか」を後から追えるようにするためです）。
   - `reviewed_at` には**レビュー実施時刻**（ISO 8601、タイムゾーン付き）を入れます。次サイクルで既処理フィードバックを除外する基準になるため、省略しないでください。
   - `image_log_count` / `feedback_count` は、`period_to` までではなく**取得期間全体**の件数です。
   - `asset_requests` には、ステップ6で Todoist に作成した設定資料画像への修正要望タスクの件数を入れます（無ければ `0`）。

2. `date` には締め切り位置（`period_to`）を渡して記録します。

   ```bash
   cd {プロジェクトルートの絶対パス}
   pnpm exec tsx src/firebase/put_doc.ts "{period_to}" "review_marker" --collection image_feedback_reviews --description-file tmp/firestore_doc.txt
   ```

   - 第2位置引数 `"review_marker"` が `type`（コレクション内識別用）。`--collection` 指定時は NOTE_TYPE 検証はバイパスされます。

3. 記録したマーカーのドキュメント ID を報告します。

---

## 出力（ユーザーへの報告）

最終的に以下を簡潔にまとめて報告してください。

1. 対象期間と取得件数（image_logs N 件 / image_feedback 件数）。
2. スコア分布と、繰り返し現れた称賛点・懸念点。
3. 偏り集計の分布表（特に `shot_size` / `camera_direction`）と、立った偏りフラグ。
4. 核 / 彩りの仕分け結果（衝突があればその判断ポイント）。
5. 提示したガイドライン修正案と、承認・反映の有無。
6. 設定資料画像（assets/images）への修正要望を Todoist に登録した場合は、その対象資料・件数・タスクタイトル。
7. 記録したレビューマーカー（`period_from` / `period_to` / `analyzed_to` と ID）。締め切り位置を取得期間の末日より手前に戻した場合は、**次サイクルへ持ち越す未評価の区間**もあわせて伝えます。マーカーを記録しなかった場合（締め切り位置が進まなかった場合）は、その理由と最初の未評価日を伝えます。
