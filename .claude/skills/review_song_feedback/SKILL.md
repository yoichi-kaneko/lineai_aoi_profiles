# review_song_feedback

碧衣の楽曲生成について、一定期間に溜まった**楽曲生成ログ（`song_logs`）**と**ユーザーフィードバック（`song_feedback`）**をまとめてレビューし、`assets/songs_guideline.md` の改善につなげるスキルです。issue #71 にあたります（画像側の柱C `review_image_feedback` の方式を流用）。

## 前提・思想

- **手動起動・月次サイクル**: 自動実行はしません。ユーザーが「楽曲レビューして」等と手動で起動したときだけ動きます。楽曲は週1生成（調べモード）のため、1サイクルの対象は4〜5曲程度が目安です。
- **読み手はこのスキルだけ**: `song_feedback` は日々の各モード（暁・望・小夜・帰灯・調べ）のコンテキストに流入しないよう専用コレクションに隔離されています（`song_logs` は調べモードの直近重複回避でも読まれます）。
- **客観的な土台**: 「似た曲調・題材が続いていないか」を主観でなく**集計**で判定します（[song_logs スキーマ](../../docs/song_log_schema.md) が土台）。ただし週1生成でサンプルが小さいため、割合よりも**回数と連続性**で見ます。
- **音声の現物確認はしない**: 碧衣は音声ファイルの中身を聴き取れないため、検証は `song_logs` に残る歌詞全文・`theme_digest`・パッケージ・ジャンル・タグと、フィードバックの文面で行います。
- **human-in-the-loop**: ガイドラインの書き換えは必ず**修正差分案を提示し、ユーザーが承認してから**反映します。勝手に `assets/songs_guideline.md` を編集しないでください。
- **「核 / 彩り」の見立て**: `songs_guideline.md` には画像側のような明示の2層宣言はありませんが、本スキルでは次のように仕分けます。
  - **核（安易に動かさない）**: セクション1-1 の固定要素（`Lead Vocal (Female, Clear, Japanese)`、`Piano` / `Crystal-like Synth Pad`）、セクション2-2〜2-3 の転写原則・禁止事項（元の出来事の特定を遮断する歌詞の安全原則）。指摘があれば**締める**方向のみ。
  - **彩り（積極的に揺らす）**: セクション4 のスタイルパッケージ、セクション5 の彩り軸、セクション2-4 の詩的語彙集、セクション6 の description テンプレート。
- **偏りの二義性（是正すべき偏り／歓迎すべき偏り）**: 彩り層の偏りには2種類あります。①評価の裏付けがない、惰性・自己選択による偏り → 是正して多様性を回復する対象。②ユーザーが好ましいと評価した要素への偏り → むしろ歓迎し、その要素の頻度・重みを意図的に高める対象。偏りの数値（ステップ3）だけでは①②を区別できないため、**必ずステップ2の評価と突き合わせて**判断します。

## 使うもの

- 取得: **get_firestore_docs** スキル（`--collection` で専用コレクションを指定）
- 修正要望の記録: **put_todoist_task** スキル ― ガイドラインの文言で直せない指摘（ステップ6）や、抽選軸の偏り強化要望（ステップ4の注釈）を Todoist タスクとして残す
- マーカー記録: **put_firestore_doc** スキル（`--collection song_feedback_reviews`）
- 参照: [song_logs スキーマ](../../docs/song_log_schema.md) / [song_feedback スキーマ](../../docs/song_feedback_schema.md) / [楽曲生成ガイドライン](../../../assets/songs_guideline.md)（参考サンプル集は `assets/songs_lyrics_samples.md`）

## 手順

### ステップ0：レビュー対象期間の決定

1. **前回マーカーの参照**: `song_feedback_reviews` コレクションから直近のレビューマーカーを探します。広めの窓（例：今日から遡って90日）で取得し、`date` が最新のドキュメントを選びます。

   ```bash
   cd {プロジェクトルートの絶対パス}
   pnpm exec tsx src/firebase/get_docs.ts "{90日前}" "{今日}" --collection song_feedback_reviews
   ```

2. **対象期間（dateFrom 〜 dateTo）を決める**:
   - **dateTo** = 今日（JST）。
   - **dateFrom** = 直近マーカーの `description.period_to` の翌日。
   - マーカーが1件も無い（初回レビュー）場合は、`song_logs` の最も古いドキュメントの日付を dateFrom にするか、ユーザーに開始日を尋ねてください。

3. 決めた期間をユーザーに一言示してから次へ進みます（例：「2026-06-08〜2026-07-08 を対象にレビューします」）。

### ステップ1：song_logs と song_feedback の取得

対象期間で両コレクションを取得します。

```bash
cd {プロジェクトルートの絶対パス}
pnpm exec tsx src/firebase/get_docs.ts "{dateFrom}" "{dateTo}" --collection song_logs
pnpm exec tsx src/firebase/get_docs.ts "{dateFrom}" "{dateTo}" --collection song_feedback
```

- 各ドキュメントの `description` は JSON 文字列です。パースして構造化データとして扱ってください（スキーマは上記スキーマ doc を参照）。
- どちらかが空でも処理は続行します（ログだけ／FBだけのレビューも成立します）。両方空なら、その旨を伝えて終了します（マーカーは更新しない）。
- 取得件数（song_logs の N、song_feedback の件数）を控えておきます。

### ステップ2：個別評価の集約（song_feedback）

`song_feedback` のフィードバック（`kind` は常に `rating`）を集約します。

- **スコア分布**: 1〜5 の各点の件数と平均（`score` が null のものは「スコアなし」として別カウント）。
- **称賛点 / 懸念点の抽出**: `comment` を読み、**繰り返し現れるポジティブ要素**（例：「歌詞の余韻が好き」「静かな曲調が沁みる」）と**繰り返し現れる懸念**（例：「似た曲調が続く」「サビが単調」）を、件数とともに箇条書きで列挙します。歌詞・曲調（パッケージ）・ボーカル・構成のどの観点への言及かを添えます。
- **対象楽曲との紐付け**: `target_date` があるコメントは同じ日付の `song_logs` と突き合わせます。`target_date` が無いものは、**投稿日以前の直近の `song_logs`**（週1生成のためほぼ一意）に紐付けて解釈します。境界（次の曲の直後など）で曖昧な場合はその旨を注記します。

### ステップ3：song_logs の傾向集計 ― 機械集計

`song_logs` の各ドキュメントから、以下を集計します。週1生成で N が小さいため、割合ではなく**回数と連続性**を基本とし、N が **4 未満**のときはサンプルが小さい旨を明記して偏り判定は参考扱いにします。

- **パッケージ分布**: `package`（正規化値 A〜G）ごとの回数。**過剰フラグ**: 同一パッケージが同サイクル内で3回以上、または前回マーカーの `summary` と照らして複数サイクル連続で最多。**欠落**: 長期（2サイクル以上）にわたり一度も選ばれていないパッケージは情報として注記（7パッケージに対し月4〜5曲のため、1サイクル内の欠落は正常です）。
- **genres / tags の頻出値**: 出現回数の上位を列挙します。パッケージ既定の値に由来する偏りか、自由裁量による偏りかを区別して注記します（テンポ感・明暗などの彩り軸は `tags` に近似的に現れます。例: `Uptempo`, `Melancholic`）。
- **題材・モチーフの反復**: `theme_digest` と歌詞（`lyrics`）を読み、繰り返し現れるモチーフ（例：雨、夜、光、稜線、窓辺）を定性的に列挙します。ガイドライン セクション2-4（詩的語彙集）への追加候補・偏り是正の材料になります。

「似た曲が続いている」というFBがあれば、この集計が**客観的な裏付け**になります。両者を突き合わせて言及してください。

### ステップ4：「核 / 彩り」仕分け

ステップ2の評価・ステップ3の偏りを、前提・思想の「核 / 彩りの見立て」に従って仕分けます。

- **核への指摘**（碧衣の声質・音楽的アイデンティティの揺らぎ、歌詞から元の出来事が特定できてしまう等）→ 核を**締める**方向。例：「歌詞が日記みたいで生々しい」→ セクション2-2〜2-3 の転写・禁止事項を補強。
- **彩りへの指摘**（曲調・題材・構成の偏りや、もっと自由に等）→ 彩りの配分を調整する方向。調整には2方向があります。
  - **広げる**（多様性の回復）: 評価の裏付けがなく惰性で偏った値を均す。例：「似た曲調が続く」＋パッケージ過剰フラグ → 該当パッケージの「適応」記述を絞る、詩的語彙集に新しい受け皿を足す。
  - **寄せる**（好ましい偏りの強化）: 称賛が繰り返された要素の頻度・重みを上げる。例：「静かな曲調が沁みる」が複数件 → パッケージB/Dの「適応」を広げる、該当タグを優先候補として明記する。
  - **抽選2軸（テンポ感 / ボーカル表現・セクション5-1）の扱い（注釈）**:
    - この2軸は**当面、一様抽選を維持**します。「寄せる（偏り強化）」の修正案はこの2軸には作りません（ステップ5でも増頻案を出さない）。画像側の構図2軸と同じく、フィードバック受付によるガイドラインの変化量が短期間に大きくなりすぎ、不安定化するリスクを避けるためです。
    - ユーザーからこの2軸への偏り強化要望が出た場合は、ガイドラインを今すぐ変えるのではなく、**put_todoist_task** で Todoist タスクとして記録し（タイトル例：`[楽曲軸要望] テンポ感：スローバラードの頻度を上げたい`）、将来の仕組み検討の材料として残してください。
    - 「広げる」方向（惰性で避けられている語彙の説明を補強する等）は、一様抽選の枠内で従来どおり扱って構いません。
- **衝突判定ルール**: 2つのFBが本当に矛盾するのは**同じ層の同じ属性**を指すときだけです。「歌詞が生々しい（核）」と「同じ曲調が続く（彩り）」は別層なので両立し、両方対応します。矛盾が生じるのは「静かな曲を増やして」対「静かな曲ばかり」のように**同じ彩りの同じ属性**へ相反要望が当たったときだけで、その場合のみ、どちらを採るか／配分をどう取るかの判断ポイントとして明示します。
- **テキストで直せない指摘の退避（ステップ5 vs ステップ6 の判定）**: ガイドラインの語彙追加・パッケージ調整・説明の補強で応えられる指摘はステップ5へ。Mureka の生成品質そのもの（音質・発音・ミックス等）や、モード実装（`modes/song.md`）・スキル実装側の変更が必要な指摘は、文言を直しても解決しないためステップ6候補として控えます。

### ステップ5：ガイドライン修正差分案の提示（承認 → 反映）

仕分け結果をもとに、`assets/songs_guideline.md` への**具体的な修正差分案**を作り、ユーザーに提示します。

- どのセクション（核 or 彩りのどの項目）を、**どう変える**かを before/after で示します。例：
  - 彩りの調整（広げる）: 惰性で続いたパッケージの「適応」を絞る／詩的語彙集（セクション2-4）に語彙を追加。
  - 彩りの調整（寄せる）: 称賛された曲調・題材を該当パッケージや自由選択軸（セクション5-2）の説明で優先候補として明記。※抽選2軸（テンポ感 / ボーカル表現）への増頻案は作らない（ステップ4の注釈参照。要望は Todoist へ記録）。
  - 核の引き締め: 出来事が透けた歌詞への対策をセクション2-3（禁止事項）・2-5（セルフチェック）に補強。
- 各案には**根拠**（ステップ2の評価件数・ステップ3の集計値）を添えます。
- **ユーザーが承認した項目だけ** `assets/songs_guideline.md` を Edit で反映します。未承認・保留の項目は反映しません。何も承認されなければガイドラインは変更しません。

### ステップ6：ガイドラインで直せない修正要望の記録

ステップ4で退避した、原因が `assets/songs_guideline.md` の**文言ではない**指摘（Mureka の生成品質、`modes/song.md` やスキル実装側の変更が必要なもの、参考サンプル集の拡充が必要なもの）を、**put_todoist_task** スキルで Todoist にタスクとして残します。要望が何も無ければ、このステップはスキップします（タスクは作りません）。

- **content（タイトル）の目安**: `[楽曲要望] ボーカルの発音が不明瞭な曲が続く` のように、`[楽曲要望]` プレフィックス＋要望の要約。
- **description（詳細）の目安**: 現状の懸念（FB の根拠・件数）、どう直されるとよいか、根拠となった対象日などを記載します。複数行にしたい場合は bash の `$'...'` クォート構文で `\n` を実際の改行として渡してください（リテラル `\n` が Todoist に保存されるのを防ぐため）。

```bash
cd {プロジェクトルートの絶対パス}
pnpm exec tsx src/todoist/put_task.ts "[楽曲要望] ボーカルの発音が不明瞭な曲が続く" $'懸念: 「日本語の発音が聴き取りづらい」という指摘が2件。\n要望: 生成時の description でボーカルの明瞭さを指定する等、モード実装側での対策を検討してほしい。\n根拠: feedback 2件 / 対象日 2026-06-14, 2026-06-28'
```

作成したタスク（タスクタイトル・件数）を控え、最終報告とステップ7のマーカーに反映します。

### ステップ7：レビュー区切りマーカーの記録

次サイクルの起点を残すため、`song_feedback_reviews` コレクションにマーカーを1件記録します。

1. マーカー本文（JSON）を `tmp/firestore_doc.txt` に Write で書き出す（put_firestore_doc の作法）。スキーマ:

   ```json
   {
     "period_from": "2026-06-08",
     "period_to": "2026-07-08",
     "reviewed_at": "2026-07-08T21:30:00+09:00",
     "song_log_count": 4,
     "feedback_count": 3,
     "guideline_updated": true,
     "requests": 1,
     "summary": "静謐系パッケージへの称賛が続き、B/Dの適応を拡張。夜・雨モチーフの反復を注記。核は変更なし。発音の指摘1件を requests に登録。"
   }
   ```

   - `requests` には、ステップ6で Todoist に作成した修正要望タスクの件数を入れます（無ければ `0`）。
   - `summary` には最多パッケージ・主要な判断を含めます（次サイクルのステップ3で「複数サイクル連続の偏り」を判定する材料になります）。

2. `date` には対象期間の末日（`period_to`）を渡して記録します。

   ```bash
   cd {プロジェクトルートの絶対パス}
   pnpm exec tsx src/firebase/put_doc.ts "{period_to}" "review_marker" --collection song_feedback_reviews --description-file tmp/firestore_doc.txt
   ```

   - 第2位置引数 `"review_marker"` が `type`（コレクション内識別用）。`--collection` 指定時は NOTE_TYPE 検証はバイパスされます。

3. 記録したマーカーのドキュメント ID を報告します。

---

## 出力（ユーザーへの報告）

最終的に以下を簡潔にまとめて報告してください。

1. 対象期間と取得件数（song_logs N 件 / song_feedback 件数）。
2. スコア分布と、繰り返し現れた称賛点・懸念点（どの楽曲への言及か）。
3. 傾向集計（パッケージ分布・genres / tags 頻出値・モチーフの反復）と、立った偏りフラグ。
4. 核 / 彩りの仕分け結果（衝突があればその判断ポイント）。
5. 提示したガイドライン修正案と、承認・反映の有無。
6. ガイドラインで直せない要望を Todoist に登録した場合は、その件数・タスクタイトル。
7. 記録したレビューマーカー（期間・ID）。
