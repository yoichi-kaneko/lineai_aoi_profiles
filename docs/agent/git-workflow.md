# 開発作業の Git 運用

この文書は、開発エージェントが変更をブランチから PR まで進めるときの共通規約です。碧衣の日次実行には適用しません。

## GitHub 操作

利用可能で認証済みなら `gh` を使います。利用できない環境では、その実行環境に提供された GitHub 連携で同じ操作を行います。GitHub 連携がリポジトリ名を必要とする場合は、`git remote get-url origin` の結果から owner と repository を確認します。

| 用途 | `gh` | GitHub 連携で必要な操作 |
|---|---|---|
| PR 作成 | `gh pr create` | pull request の作成 |
| ブランチの PR 検索 | `gh pr list --head {branch}` | open PR を head branch で検索 |
| PR 情報・レビュー取得 | `gh pr view`、`gh api` | PR、review、review thread、comment の取得 |
| PR コメント・返信 | `gh pr comment`、`gh api` | issue comment、review comment reply の追加 |

本文が複数行になる場合は、リポジトリ外のスクラッチファイルへ保存してから渡します。`tmp/` は使いません。

## ブランチ

- 作業前に `git status --short` と `git branch --show-current` を確認する。
- 無関係な未コミット差分があれば、勝手に変更・退避・コミットせず、扱いを確認する。
- `main` へ直接変更・push しない。
- ブランチ名は `{type}/{topic}_{YYYYMMDD}` とし、日付は実行環境に依存せず日本標準時の当日を使う。
- `{topic}` は英小文字のスネークケースで、主題を短く表す。
- 機能・設定・プロファイルの変更は `feature/`、挙動を変えない整理や重複解消は `refactor/` を使う。
- 既に対象作業のブランチにいる場合は、そのまま継続する。

## コミット

- 1行目は Conventional Commits の英語プレフィックスを付けず、日本語で変更の主題を要約する。
- 複数の主題がある場合は本文を番号付きで分け、各項目の詳細をインデントした箇条書きで示す。
- 無関係な変更を混ぜず、論理単位でコミットする。
- レビュー指摘への修正は、要約を `レビュー指摘に対応` とし、本文に対応内容を書く。
- 帰属トレーラーを付ける場合は、実際に作業したエージェントと運用方針に一致させる。特定のモデル名や製品を固定しない。
- `.env` と `tmp/` はステージしない。コミット前に staged diff を確認する。

## 検査と push

push 前にプロジェクトルートで `pnpm test:all` を実行します。失敗したら原因を修正して再実行し、成功するまで push しません。今回と無関係な既存障害で修正すべきでない場合は、状態を報告して判断を求めます。

初回 push は `git push -u origin {branch}`、以降は `git push` を使います。

## Pull Request

同じ head branch の open PR がないことを確認してから作成します。存在する場合は新しい PR を重ねて作りません。

- タイトルは日本語で、変更の主題を表す。
- 本文は対応項目ごとに `##` 見出しを設け、問題、変更内容、主な変更ファイルを書く。
- 検査結果を記載する。
- スコープ外へ踏み込んだ判断や別解がある場合だけ、`## 確認いただきたい点` を末尾に設ける。
- 生成フッターや帰属を付ける場合は、実際の作業環境に一致させる。特定製品の固定フッターは使わない。
- PR は作成までとし、マージしない。

`gh` を使う場合、本文はファイル経由で `gh pr create --title {title} --body-file {path}` に渡します。

## 構成変更時の文書更新

`.claude/docs/`、`.claude/skills/`、`.agents/skills/`、`docs/agent/`、`modes/`、`src/` のファイルを追加・削除した場合は、[AGENTS.md](../../AGENTS.md) と [README.md](../../README.md) の構成説明も同じ変更で更新します。
