※一週間のうちに灯った出来事を振り返り、その週に訪れた場所の配置をもとに、プラネタリウム装置「天縫（あまぬい）」が投影する星座として届けます。

以下は仮組みの手順です。**注記** は、未決定の事項や実装が追いついていない箇所を示します。

### モードの位置づけ

- **モード名・キー**: 結星（ゆいぼし）／標準モードキー `weekly`／入力トリガー `daily message (結星): YYYY-MM-DD`
- **宛先**: ユーザー個人宛（destination: user）。家族グループへは送りません。
- **送信時間帯**: 月曜の深夜（00:00〜04:59 JST）。日曜の小夜の申し送り（`night_handover`）と、日曜の夜のチェックインまでを振り返りに含めるため、週が明けてから実行します。
- **起動方法**: [run_aoi_weekly](../.claude/skills/run_aoi_weekly/SKILL.md) スキル（対話モードでの手動起動）、または `send_daily_line.sh weekly`（ヘッドレス実行）です。どちらも、実行時刻が月曜 00:00〜04:59 の外であれば起動せず、同じ日付の `run_logs`（`mode: weekly`）があれば実行済みとしてスキップします。
- **対象期間**: トリガーの日付（月曜）の**前日までの7日間**、つまり前週の月曜〜日曜です（以下「対象期間」）。例：トリガーが `2026-10-05` なら、対象期間は `2026-09-28`〜`2026-10-04` です。トリガーの日付（月曜）そのものは含めません。
- **分量**: 一週間を振り返るメッセージとして、日次モードより多くなって構いません。
- **天縫（あまぬい）**: 碧衣が扱うプラネタリウム装置です。設定は [../.claude/rules/aoi_character.md](../.claude/rules/aoi_character.md) の「プラネタリウム装置：天縫（あまぬい）」、外観・投影のイメージは設定資料 [../assets/images/amanui.png](../assets/images/amanui.png) を参照してください。

- **暁との関係**: 結星は月曜の深夜に届き、同じ月曜の朝には暁が届きます。暁も日曜の `night_handover` を読むため、結星が届けた内容は `weekly_handover` として暁へ引き継ぎ（ステップ7）、暁はそれを踏まえて言葉を選びます（[morning.md](morning.md) ステップ3の補足）。

### ステップ1：一週間の申し送りを読み返す

一週間に何があったかは、小夜モードが毎晩残す **`night_handover`（一日の概要）の7日分**から把握します。小夜はその日の Firestore の記録（暁・望・門灯・継灯・帰灯・綴葉・響の申し送りや、ユーザーの言葉）を読んだうえで一日をまとめているため、出来事の把握にほかの `type` は使いません。あわせて、**前週の結星が残した `weekly_handover`** を読み、前週と同じ星座・同じ話題を繰り返さないための確認に使います。

次の2つの取得は互いに独立しているため、並列で呼び出して構いません。

1. **`get_firestore_docs` スキル**で、対象期間（`dateFrom` に初日＝トリガーの日付の7日前、`dateTo` に末日＝トリガーの日付の前日）の `night_handover` を取得してください。7日分を絞らずに取得すると入力が大きく膨らむため、必ず `--type` を付けてください。

```bash
pnpm exec tsx src/firebase/get_docs.ts "{初日}" "{末日}" --type "night_handover"
```

2. **`get_firestore_docs` スキル**で、前週の結星の `weekly_handover` を取得してください。前週の結星は対象期間の初日（前週の月曜）に実行されているため、日付は初日だけを指定します。

```bash
pnpm exec tsx src/firebase/get_docs.ts "{初日}" "{初日}" --type "weekly_handover"
```

3. 手順1で取得した各日の記録から、その週に何があったかを振り返ってください。後続のステップ3（②の中心）と、ステップ5・6（画像と本文）の素材になります。
4. `night_handover` の無い日（小夜が実行されなかった日など）があっても、ほかの `type` で補わず、記録のある日だけで一週間を振り返ってください。無い日の出来事を推測で補わないでください。
5. 手順2の `weekly_handover` からは、前週に届けた**主役の星座**・**本文で触れた話題**・**一週間の要約**を控えておいてください。ステップ5・6で重複を避けるためだけに使い、今週の出来事の素材にはしません。記録が無い場合（前週に結星が実行されなかった場合など）は、重複の確認をせずに進めてください。

### ステップ2：一週間のチェックイン記録を取得する

1. **`get_swarm_checkins` スキル**で、対象期間（`start_date` に初日、`end_date` に末日）のチェックインを取得してください。
2. 各チェックインの `venue.lat` / `venue.lng` / `venue.id` を、ステップ3の入力に使います。

> **注記（利用条件）**: Swarm（Foursquare）由来の座標の利用条件は問い合わせの回答待ちです。現時点で [select_locations](../.claude/skills/select_locations/SKILL.md) / [plot_locations](../.claude/skills/plot_locations/SKILL.md) は、Swarm のチェックイン座標を入力にしない取り決めになっています。回答を受けて、本ステップ以降を見直します。

> **注記（座標の受け渡し）**: 1週間分の出力を読んで全座標を手で書き写すと、誤りが起きやすくトークンも多く使います。Swarm の出力から `{ lat, lng, placeId }` の配列を直接ファイルへ書き出す変換（`get_checkins` のオプション、または小さな CLI）を用意する予定です（未実装）。

### ステップ3：描画する座標を2候補選び、それぞれ点描画PNGを生成する

ステップ2のチェックインを、[select_locations](../.claude/skills/select_locations/SKILL.md) の入力形式（`{ "lat": 数値, "lng": 数値, "placeId": 文字列 }` の配列。`placeId` には `venue.id` を入れ、同じ施設への訪問は1件ずつ別の要素として並べる）で `tmp/select_locations_input.json` に保存してください。そのうえで、次の2候補を作ります。

#### 3-1. 集合化（③）で集約する

```bash
pnpm exec tsx src/geo/select_locations.ts "tmp/select_locations_input.json" "tmp/plot_cluster.json" --method cluster
pnpm exec tsx src/image/plot_locations.ts "tmp/plot_cluster.json" "tmp/location_plot_cluster.png"
```

週全体の訪問範囲を要約した候補になります。

#### 3-2. 中心から近い順に選ぶ（②）

1. **中心を決める**: ステップ1で振り返った出来事のうち、碧衣が**その週で最も重要度が高い**と判断したものを1つ選び、その場所の座標を中心とします。
2. **中心を指定して選ぶ**: その座標を `--center` に渡してください。

```bash
pnpm exec tsx src/geo/select_locations.ts "tmp/select_locations_input.json" "tmp/plot_nearest.json" --method nearest --center "{緯度},{経度}"
pnpm exec tsx src/image/plot_locations.ts "tmp/plot_nearest.json" "tmp/location_plot_nearest.png"
```

その出来事へ焦点を当てた候補になります。中心から半径 30km の外にある地点は描かれません。

#### 共通の扱い

- 各実行の標準出力（要約 JSON）を控えておいてください。ステップ4の比較に使います。
- 要約の `pointCount` が0の候補は、描ける点が無いため PNG を作らず、候補から外してください（`--center` の半径内に地点が無い場合も0になります）。
- 座標（入力・出力の JSON、中心の座標）は位置情報です。報告本文や Firestore の記録へ転記しないでください。

> **注記（中心の座標の出どころ）**: 重要な出来事にチェックインがある場合は、そのチェックインの `venue.lat` / `venue.lng` を使う想定です。チェックインの無い出来事（山頂でチェックインしていない日など）の座標をどこから得るか（`get_openweather_forecast` のジオコーディング結果、計画書など）は未決定です。

> **注記（中心が決まらない週）**: 重要な出来事の座標が得られない週に、`--center` を省略して自動判定（地点が最も集まる場所）へ戻すか、②を省いて③だけにするかは未決定です。

> **注記（参考画像向けの描き方）**: 配置図は星座の着想の種として渡し、点の位置の再現は求めません（[../assets/weekly_image_guideline.md](../assets/weekly_image_guideline.md) セクション5-1）。そのため、点を大きくする、訪問回数で明るさを変える、といった参考画像向けの描画オプションを `plot_locations` に加えることは必須ではありません。実際の生成結果を見て、着想の種として弱すぎる場合に検討します。

### ステップ4：2枚のPNGを比較し、どちらかを選ぶ

1. ステップ3で作った PNG（`tmp/location_plot_cluster.png` / `tmp/location_plot_nearest.png`）を Read ツールで確認してください。
2. 2枚を見比べ、点の配置のバランスがよいほうを1枚選んでください。
3. 候補が1枚しか残らなかった場合は、比較せずにその1枚を使います。

> **注記（選ぶ基準）**: 点の配置の再現は求めないため、2枚の比較は「どちらが星座の着想の種としてふさわしいか」の判断になります。黒地に白い点の2枚を見比べて「バランス」を判断させると、結果がぶれやすいと思われます。②は「焦点」、③は「全体の要約」と性格が分かれるため、「その週に合うのはどちらか」を主な基準とし、要約の数値（`represented` / `pointCount`）を補助に、画像は確認に使う案があります。両方式がほぼ同じ結果になる週は、比較そのものを省く案もあります。いずれも未決定です。

> **注記（候補が無い週）**: 2候補とも作れなかった週（チェックインが0件、または点がごく少ない週）に、画像をやめるか、データに依らない星座を描くかは未決定です。

### ステップ5：天縫が投影する星座の画像を生成する

ステップ4で選んだ配置図（点描画PNG）と、ステップ1・2で振り返った一週間をもとに、天縫がドームに星座を投影している画像を生成します。**画像生成の規則は [../assets/weekly_image_guideline.md](../assets/weekly_image_guideline.md) を正とします。** 主役の星座が何の姿かは碧衣が決めず、画像生成モデルに委ねます。

1. **週の要約をまとめる**: ステップ1・2で振り返った一週間から主な出来事を3〜5つ選び、1行に1つずつの要約にしてください。書き方はガイドラインのセクション6に従います。前週の「一週間の要約」（ステップ1の手順5）と同じ種類の出来事（毎週続く習慣など）があっても、それを要約の中心に据えず、その週ならではの出来事を優先してください。
2. **画像を生成する**: ガイドラインのセクション7の手順（3軸の抽選 → プロンプトの構成 → `review_with_codex`（観点セット `weekly_image_prompt`）によるレビュー → 生成と品質チェック）に従ってください。添付する配置図は、ステップ4で選んだ PNG です。前週の主役の星座が分かっている場合は、その姿を避ける対象としてプロンプトへ加えます（ガイドラインのセクション5-5）。
3. 生成した画像のファイルパスを保持してください。ステップ6で送ります。

> この画像は `image_logs` に記録しません。識別子（`image_id`）も本文へ添えません（ガイドラインのセクション7）。

> **注記（出来事の選び方）**: 週の要約にどの出来事を選ぶか（ステップ3-2で中心に据えた出来事を必ず含めるか、など）は未決定です。

> **注記（生成に失敗した場合）**: 再生成しても画像が得られない場合、または品質チェックの重大な問題が解消しない場合に、テキストだけを送るか、送信をやめるかは未決定です。

### ステップ6：本文を書き、画像と一緒に送る

1. ステップ5で生成した画像を Read ツールで確認し、主役の星座が何の姿として描かれたかを読み取ってください。その星座と、ステップ1・2で振り返った一週間をもとに、碧衣がユーザーへ宛てた本文を書いてください。口調・語彙・世界観は [../.claude/rules/aoi_character.md](../.claude/rules/aoi_character.md) と [../.claude/rules/aoi_messaging.md](../.claude/rules/aoi_messaging.md)（ユーザー個人宛）に従います。
   - **前週との重複を避ける**: 前週の「本文で触れた話題」（ステップ1の手順5）と同じ話題を、同じ切り口や言い回しで繰り返さないでください。前週から続く出来事に触れる場合は、前週の便りを踏まえた続きとして書きます。ただし、前週の `weekly_handover` に送信の失敗が記されている場合は、前週の便りが届いている前提の書き方をしないでください。
2. **`send_line_image` スキル**（送信先: `user`）で、生成画像と本文を**1回のリクエスト**で送信してください（表示順: 画像 → テキスト）。本文の保存先・送信失敗時の Firestore 退避は [send_line_image](../.claude/skills/send_line_image/SKILL.md) の SKILL.md に従います。
3. 送るのはステップ5で生成した画像1枚だけです。配置図（点描画PNG）は送りません。
4. このモードは **`aoi.md` の共通ステップ：LINE送信（`send_line_text`）を使用しません**。

> **注記（本文の構成）**: 週次モードの本文は、一週間のうち別々の日の出来事を2〜3つ選んでその繋がりを綴る「結び」（一週間に一つだけ題を付け、一日ごとの列挙はしない）として構想されていました。本ステップの本文が「結び」を置き換えるのか、両方を残すのかは未決定です。碧衣自身の一週間（ルリの飛んだ先、蛍・漆との相談、その週に入った手入れ）に触れる節を設けるかも、あわせて決めます。

### ステップ7：暁への引き継ぎ記録

ステップ6の送信の後（LINE送信が失敗した場合でも）、**`put_firestore_doc` スキル**を使用し、同じ月曜の朝の暁モードへ引き継ぐ情報を記録してください。暁はこの記録を読み、結星で届けた話題を繰り返さないように言葉を選びます。翌週の結星も、星座や話題の重複を避けるためにこの記録を読み返します（ステップ1の手順2）。

- **日付**: トリガーの日付（月曜。実行日）
- **type**: `weekly_handover`（[../src/firebase/noteTypes.ts](../src/firebase/noteTypes.ts) の `NOTE_TYPE.WEEKLY_HANDOVER`）
- **記録内容**: 以下を必ず含めてください。
  - **送信の成否**: 結星の便りが届いたか、送信に失敗して `line_undelivered` へ退避したか（暁が「届いている前提」で書いてよいかを判断する材料となるため必須）
  - **一週間の要約**: ステップ5でまとめた週の要約（3〜5行）
  - **本文で触れた話題**: 本文で取り上げた出来事。とりわけ前日（日曜）の出来事に触れたかどうかを明記してください（暁も日曜の `night_handover` を読むため）
  - **主役の星座**: ステップ6で読み取った、主役の星座の姿（翌週の結星が、同じ姿を避けるために使います）
  - **特記事項**（任意）: 暁に触れてほしいことがあれば1行程度で添える
- 座標などの位置情報は記録しないでください（ステップ3の「共通の扱い」）。
- **記録手順**: [aoi.md の「共通ステップ：Firestoreへの記録」](../aoi.md) に従ってください。
